# 技术文档写作规范（项目级，负责人指令 2026-09-09）

## 什么时候用这个 skill

写、改、翻译任何项目文档时：`docs/` 下的设计文档、看板、changelog、周报、指南，以及提交信息、代码注释里的长段说明。**写完后必须做一遍"去黑话检查"（见文末）。**

## 基本要求

1. 使用自然、直接、工程师日常会使用的中文。
2. 不要为了显得专业而创造抽象术语、隐喻或黑话。
3. 优先描述"**谁做什么、输入是什么、输出是什么、什么时候发生、失败时怎么办**"。

## 禁用词表（写机制描述时禁用；专名除外）

闸门、卡点、抓手、闭环、拉通、对齐、沉淀、赋能、冻结、水位、护栏、兜底、打平、击穿，以及自造的"对账腿/链路腿/消费腿"这类"XX 腿"。

例外——已定义的项目专名可直接用，但优先补一句具体所指：
- 契约①~④：指四份已命名的 Schema/接口定义文件（requirement_spec / PLCopen XML 生成规则 / io_map / acceptance）。日常行文优先写"接口定义/Schema"；
- 冻结：仅指版本停止修改（feature freeze）。其余场合写"停止修改该版本"或"固定使用版本 v1.3"。

## 替换原则（抽象 → 具体动作）

| 不要这样写 | 这样写 |
|---|---|
| 设置一道闸门 | 增加一次校验 / 只有满足以下条件才允许进入下一步 |
| 接口契约 | 接口定义、接口约定（确实在讨论 schema contract / contract testing 时才用"契约"） |
| 冻结数据 | 停止修改该版本数据 / 固定使用 v1.3 |
| 对账腿 | 写出具体对象：如"AML 侧地址与生成代码里的地址比对" |
| 建立异常兜底机制 | 直接写实际动作：如"调用失败后重试 3 次；仍失败则记录任务状态并进入人工处理队列" |

## 推荐的段落结构（功能/流程描述优先用这个）

```
目的：   为什么需要这个功能。
输入：   系统收到什么数据。
处理流程：按实际执行顺序描述步骤。
输出：   最终产生什么结果。
异常情况：可能出现什么错误，以及系统如何处理。
```

## 不要做的事

- 不要用新名词概括一句就能说清的动作；
- 不要把简单流程包装成抽象概念；
- 不要为每个机制起名字；
- 不要使用没有明确定义的企业黑话；
- 一个术语若不是行业通用术语、也不是本文已定义的术语，就不用。

## 写完之后的"去黑话检查"（必做）

逐句检查是否存在可以换成具体动作的抽象名词。有，就改写成普通工程师第一次阅读就能理解的表达。检查顺序：

1. 搜禁用词表命中；
2. 搜"能力/体系/机制/体系化/一体化"这类概括性后缀，问一句"它具体指什么动作"；
3. 搜自造复合词（XX 腿、XX 面、XX 位），换成具体对象；
4. 长句拆短：一句话只说一个动作。
