# 技术文档写作规范（项目级，负责人指令 2026-09-09；2026-09-11 增补专名白名单与全量排查流程）

## 什么时候用这个 skill

写、改、翻译任何项目文档时：`docs/` 下的设计文档、看板、changelog、周报、指南，各目录的 README，`contract/` 下的说明文档，以及提交信息、代码注释里的长段说明。批量排查或优化旧文档、旧注释时，按文末"全量排查流程与多轮校验"执行。**写完后必须做"去黑话检查"（见文末）。**

## 基本要求

1. 使用自然、直接、工程师日常会使用的中文。
2. 不要为了显得专业而创造抽象术语、隐喻或黑话。
3. 优先描述"**谁做什么、输入是什么、输出是什么、什么时候发生、失败时怎么办**"。
4. **只改措辞，不改含义**：优化已有内容时，事实、数据、日期、决定、状态一律保持原样；原文技术内容说不清的，保持原样或标注待确认，不要脑补。

## 禁用词表（写机制描述时禁用；已定义专名除外）

闸门、卡点、抓手、闭环、拉通、对齐、沉淀、赋能、冻结、水位、护栏、兜底、打平、击穿，以及自造的"对账腿/链路腿/消费腿"这类"XX 腿"。

例外——已定义的项目专名可直接用，但优先补一句具体所指：
- 契约①~④：指四份已命名的 Schema/接口定义文件（requirement_spec / PLCopen XML 生成规则 / io_map / acceptance）。日常行文优先写"接口定义/Schema"；
- 冻结：仅指版本停止修改（feature freeze）。其余场合写"停止修改该版本"或"固定使用版本 v1.3"。

## 已定义项目专名白名单（可用；首次出现要让新读者看懂具体所指）

本表与 `docs/项目术语通俗手册.md` 保持同步；两处冲突时以术语手册为准，并回改本表。

| 专名 | 具体所指 | 使用限制 |
|---|---|---|
| 闸门 1~4 / gate | 编排流水线的四个质量检查步骤（生成 → 静态检查 → 三方一致性检查 → 部署+在线验收），产物为 `runs/**/gate.json` | 可作专名，如"闸门 2 静态检查"；泛指一道检查时写"质量检查步骤/校验"，不写"设一道闸门" |
| 半环 / 全环 / 全闭环 | 半环 = 生成→部署→脚本验收已在转；全环 = 再加物理仿真、自动判定、失败回喂 AI 重写，循环到合格 | 仅作这条循环的名词；不得当动词或万能词（"闭环一下这个问题"❌）；每篇文档首次出现时把循环内容写全 |
| 链路 A / 链路 B | 链路 A = 程序编译成 DLL 在 Python 进程内直接调用；链路 B = 部署到 OpenPLC 走 Modbus TCP | 可用 |
| L1 / L2 / L3、R1~R6、lockstep、双链路联调、回环 | 见术语手册（测试分层、一致性检查项、步进同步等） | 可用 |
| 卡点 | 无专名含义 | 不进白名单：换成"被卡住的事项 / 等某人决定的事" |

## 常见误伤（这些不要改）

- **对齐**的工程含义：字节对齐、坐标对齐、机械对齐、地址对齐等技术用法保留；禁用的只是"拉通对齐一下"式的会议黑话。
- 代码标识符、文件名、JSON 字段名（`gate.json`、`freeze`、`gate_score` 等）：一律不改。
- 引号内的原文引用（引用历史文档、日志、报错原文）：保持原样。
- 行业通用术语（如控制理论里的"闭环控制/位置环闭环"）：保留，但优先补一句具体所指（如"闭位置环：驱动器每周期按 PLC 下发的位置目标校正实际位置"）。

## 替换原则（抽象 → 具体动作）

| 不要这样写 | 这样写 |
|---|---|
| 设置一道闸门 | 增加一次校验 / 只有满足以下条件才允许进入下一步 |
| 接口契约 | 接口定义、接口约定（确实在讨论 schema contract / contract testing 时才用"契约"） |
| 冻结数据 | 停止修改该版本数据 / 固定使用 v1.3 |
| 对账腿 | 写出具体对象：如"AML 侧地址与生成代码里的地址比对" |
| 建立异常兜底机制 | 直接写实际动作：如"调用失败后重试 3 次；仍失败则记录任务状态并进入人工处理队列" |
| 全项目的卡点 | 全项目被卡住的事（谁欠谁一个决定/一个接口） |
| 形成闭环 / 闭环掉它 | 写明循环本身：如"生成→部署→验收→失败回喂 AI 重写，循环到合格" |

## 推荐的段落结构（功能/流程描述优先用这个）

```
目的：   为什么需要这个功能。
输入：   系统收到什么数据。
处理流程：按实际执行顺序描述步骤。
输出：   最终产生什么结果。
异常情况：可能出现什么错误，以及系统如何处理。
```

## 不要做的事

- 不要用新名词概括一句就能说清的动作；
- 不要把简单流程包装成抽象概念；
- 不要为每个机制起名字；
- 不要使用没有明确定义的企业黑话；
- 一个术语若不是行业通用术语、也不是本文已定义的术语，就不用；
- 不要为了去黑话改掉事实、数据、日期、决定或状态——措辞优化不等于内容重写。

## 全量排查流程的范围

**要查要改**：`docs/**/*.md`；根目录 README、`contract/README.md`、`contract/组件契约表.md`、`runtime/README.md`、`runtime/legacy_opcua/README.md`、`scenegen/README.md`；全部 `.py` 文件的注释与 docstring。

**不改**：`runs/`、`scenegen/out/`、`toolchain/tests/out_*`、`workspace/`（生成产物与第三方代码）；`.venv/`、`.history/`、`__pycache__/`、`.pytest_cache/`；JSON 数据文件的内容（可能被测试断言）；代码里的字符串字面量、日志与报错文案；`src/agent/prompts/*.md`（运行时加载的 LLM 系统提示词，改动即行为变更，如需修改走单独评审）；文件名与目录名（即使含禁用词——改名会断链接，除非负责人另行决定）。

**历史记录**（changelog、周报、devlog）：只修措辞；事实、日期、决定、状态图标不动。

## 代码注释专项规则

1. 只允许改 `#` 注释与 docstring；任何可执行代码、字符串字面量、日志与报错文案一律不动。
2. 改完必须跑测试（`pytest`），改前改后结果完全一致才算通过。
3. 注释同样遵守禁用词表与专名白名单；英文注释里的项目专名（gate、lockstep）不受中文禁用词表限制。

## 写完之后的"去黑话检查"（多轮校验，必做）

逐句检查是否存在可以换成具体动作的抽象名词。有，就改写成普通工程师第一次阅读就能理解的表达。

**第一轮：禁用词 grep。** 对每个改过的文件搜禁用词表全文；命中先对照"常见误伤"和"专名白名单"判断是否该改，再动手。同时搜"能力/体系/机制/体系化/一体化"这类概括性后缀，问一句"它具体指什么动作"；搜自造复合词（XX 腿、XX 面、XX 位）；长句拆短，一句话只说一个动作。

**第二轮：逐段通读。** 对每个改过的段落问两个问题：① 五问（谁做什么/输入/输出/何时/失败怎么办）是否仍能答出；② 与原文相比技术含义是否不变（用 `git diff` 逐段对照）。

**第三轮：代码校验。** `git diff` 确认代码文件只动了注释与 docstring；全量跑 `pytest`，结果与改前一致。

**第四轮：交叉检查。** 文内链接指向的文件、标题仍然存在；文件名未变；changelog/周报的事实与日期未变；专名白名单与术语手册仍一致。
