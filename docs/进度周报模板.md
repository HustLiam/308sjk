# 本周总体进度

## 总体目标

工厂的人把工艺需求说出来（比如"三个轴按这个轨迹走，画个圆"），再给一份设备描述文件。AI 理解需求后，自动生成标准格式的 PLC 程序（PLCopen XML），自动部署到一个软 PLC 上跑起来，再接到仿真环境里让设备"真动起来"，仿真结果自动判定合格不合格——不合格就把错误信息喂回给 AI 重写，直到验收通过。全程不用人碰，最后人拿到的是一份验证过的、能直接下到真实 PLC 的程序。

# 智能体侧

## Agent 组成（src/agent/）

- **⓪ AML 解析器**（aml_parser.py）：IEC 62714 设备描述 → 设备模型（设备清单 / IO 点位与地址 / 拓扑 / 运动学轴参数），确定性解析、非 LLM；
- **① 需求理解**（requirement.py + spec_validator.py）：自然语言 + 设备模型 → 需求规格 requirement_spec.json；io_list 从设备模型锚定预填、语义规则校验、对话式回显与自然语言修正；
- **②a PLC 代码生成器**（pipeline.py + patternlib.py + prompts/plcgen_skill.md）：LLM 生成 PLCopen XML，"生成→闸门→结构化错误回灌修复"循环；
- **轨迹规划**（trajectory.py）：画方/画圆确定性步表——LLM 只负责认形状、抽数字，几何与验收逐字对齐；
- **②b 场景描述生成器**（scene_gen.py）：按物理仿真侧契约包 v1.1 确定性生成 scene.spec.json（内嵌 io_map）；
- **三方一致性检查器**（consistency_check.py）：XML 定位变量 ≡ io_list ≡ io_map 逐条对账（名称/方向/类型/地址六条规则）；
- **闭环编排器**（orchestrator.py）：五闸门串联（静态契约→一致性→场景自检→真编译部署→在线验收）、失败反馈包拼装、定向修复与全新生成策略、final 冻结；
- **归因与学习**（attribution.py + knowledge/pitfalls.json 坑库 + memory.py 经验库）：错误先按签名命中坑库引用修法，未命中 LLM 兜底；同质失败自动提炼泛化经验并预注入后续同类任务首轮；
- **对话式入口**（chat.py）：一条对话走完 解析→需求确认→生成→闸门→交付，闸门环境自动探测。

## 已实现功能（定性）

- **一句话需求到可交付代码**：用户只需用自然语言说清工艺意图（如"画一个正方形"）并提供设备描述文件，系统自动完成需求规格整理、PLC 控制程序（PLCopen XML，唯一代码交付格式）与仿真场景描述的生成，验证全部通过后自动冻结交付，全程无需人工写代码；
- **分层校验、失败自动返工**：每轮产物要连过五道关卡——格式契约检查、三方信号对账、场景自检、真实编译、在线验收；能在便宜关卡拦住的问题绝不拖到贵的关卡，任何一关失败都会把具体错误整理成清单回喂给模型定向修复，改完自动重跑，直到全部通过或达迭代上限；
- **规则管几何、模型管编码**：对"画方形/画圆"这类绘图需求，几何路线由确定性程序算出权威步表，语言模型只负责把步表忠实翻译成标准 PLC 代码、不许自由发挥——生成质量因此稳定，同一需求可参数化复用；
- **场景生成严格守契约**：组件种类、参数与信号、坐标单位都以物理仿真侧发布的契约包为唯一依据，不合规的产物在本地自检即被拦下；通信地址分配统一交由仿真侧按固定规则完成，两侧不会各说各话。

# PLC仿真侧
由于轴对象、工艺对象、以及类似倍福那种mc运动库中的各种模块、底层连接EtherCAT这些概念都是不完全属于iec61131-3的，而61131-10是基于61131-3的交换形式，直接使用倍福、西门子plc的编程库、模块，在开源PLC Runtime中无法运行，需要要自定义一套基于61131-3的简单规则，只使用61131-3代码子集来作为智能体程序生成和仿真的基础。
目前我们先抽象自定义一套轴对象结构，然后基于PLC Open Motion Control的标准来自定义一套运动控制模块，以便上层智能体生成代码直接调用。
## 轴对象（Axis Object）概念
```
一个"轴对象" = 插补引擎实例 + 轴参数 + IO 绑定
                │              │          │
                │              │          └─ 位置指令输出 / 编码器反馈输入的 %QW 地址
                │              └─ 行程范围、最大速度、加速度、到位窗口
                └─ INTERP FB 实例（梯形轨迹规划，每扫描输出一个插补点）
```
在生成方案中，轴对象是一个声明式定义，agent 只需提供参数，模板自动展开为 ST 代码：
```
{
  "axes": [
    { "name": "x", "travel": [0, 800], "unit": "mm",
      "vmax": 200, "accel": 500, "poswin": 2,
      "io": { "cmd": "%QW10", "fb": "%QW0" } },
    { "name": "z", "travel": [0, 300], "unit": "mm",
      "vmax": 100, "accel": 300, "poswin": 1,
      "io": { "cmd": "%QW11", "fb": "%QW1" } }
  ]
}
```
## PLCopen Motion Control 对齐
MC 块命名与语义对齐 PLCopen MC Part 1 单轴子集，作为应用层的固定 API
| MC 块 | 输入（要点） | 输出 |
|---|---|---|
| `MC_Power` | Enable, EnablePositive/Negative（CiA402 不分方向，仅门控） | Status, Busy, Error |
| `MC_Reset` | fire | Done, Busy, Error |
| `MC_Stop` | fire（电平）, v_act | Done, Busy, Error |
| `MC_Halt` | fire, ax_busy | Stopping, Done, Busy, Error（受控减速停不失能） |
| `MC_MoveAbsolute` | fire, Position, Velocity/Acceleration/Deceleration, sw, abort_bus | Done, Busy, Active, CommandAborted, Error, ErrorID |
| `MC_MoveRelative` | fire, Distance, ActualPosition, 动力学, sw, abort_bus | 同上（绝对目标 = 触发时实际位置 + Distance） |
| `MC_MoveJog` | JogForward/Backward, Velocity, cur_pos, sw | Busy, Error（起跳锚定实际位置） |
| `MC_Home` | fire, sw | Done, Busy, Error |
| `MC_ReadStatus` | Enable, sw, interp_busy, v_act | Valid, Moving, StandStill, Disabled, ErrorStop |
| `MC_ReadActualPosition` | Enable, ActualPosition | Valid, Position |

# 遇到的难点

1. **智能体侧：单次仿真迭代平均用时较长**：一轮闭环串行经过 LLM 长文生成、静态闸门、真编译部署、在线验收执行四段，任何一段失败都要整轮重来——迭代轮数与单轮时延相乘，任务收敛周期明显偏长。现有的经验预注入、权威轨迹步表、零推进熔断、段级 fail-fast 等手段都在压缩轮数，但单轮时延仍同时受 LLM 生成速度与运行时链路制约，属于当前闭环提速的主要瓶颈。
