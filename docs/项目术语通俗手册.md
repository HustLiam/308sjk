## 1. 先用一段话讲清整个项目

用户说出工艺需求（一句话）+ 提供设备描述文件 → **AI 理解需求、写出标准格式的 PLC 程序** → 自动部署到软 PLC 上跑起来 → 接进**物理仿真**让虚拟设备真动 → **自动判定**合格与否 → 不合格把错误喂回 AI 重写 → 循环直到合格。人最后拿到一份验证过的、能下到真 PLC 的程序。

三个人的分工：**lx 管"让程序跑起来"（PLC 执行侧）｜csk 管"造虚拟世界试程序"（仿真验证侧）｜gc 管"AI 本身"（智能体与闭环侧）**。

## 2. 系统模块编号（⓪①②a…这些数字是什么）

架构 v2.0 把系统拆成编号模块，看板和文档里都用编号指代。**按数据流向排**：

| 编号 | 名字 | 大白话 |
|---|---|---|
| ⓪ | AML 解析 | 先读设备描述文件（工厂电气设计软件导出的"设备清单"），把有什么设备、什么 IO 点、几根轴提取成一份结构化数据。**不是 AI 猜的，是机械提取**（同样输入必得同样输出，叫"确定性"） |
| ① | 需求理解 | AI 把用户的自然语言 + ⓪ 的设备模型，变成一份结构化需求规格：要哪些 IO 变量、什么动作、怎样算验收通过 |
| ②a | PLC 代码生成 | AI 按规矩写出 PLC 程序（PLCopen XML 格式） |
| ②b | 仿真环境生成 | AI 按规矩写出仿真场景描述（有哪些部件、尺寸、行程） |
| ③a | PLC 执行引擎 | 让程序真跑起来的那套 machinery（部署、编译、运行） |
| ③b | 仿真引擎 | 让虚拟设备真动起来的物理仿真（MuJoCo） |
| ④ | 验证与反馈 | 裁判 + 复盘：判定引擎判合格与否，归因引擎分析错在哪，回喂给 AI 重写 |

②a 和 ②b 是"平级的一对生成器"（一个生代码、一个生场景），③a 和 ③b 是"平级的一对执行者"（一个跑程序、一个跑物理）。

## 3. 两条链路（"链路 A / 链路 B"）

同一份 PLC 程序有**两种跑法**，都要支持：

| | 链路 A | 链路 B |
|---|---|---|
| 怎么跑 | 程序编译成动态库（DLL），直接在 Python 进程里当函数调用 | 程序部署到 **OpenPLC**（一个开源软 PLC），走网络通信 |
| 通信 | 没有——同进程直接调 | Modbus TCP（工业最通用的通信协议，走网口） |
| 优点 | 快、紧密同步、不依赖外部服务 | 跟真实 PLC 行为一模一样，测出的问题更"真" |
| 用途 | 将来跟仿真引擎做高速联合仿真 | 现在的日常验收 + 未来接真实设备 |

- **lockstep（步进同步）**：链路 A 的玩法——仿真每走一步，PLC 也算一步，严格同节奏，不允许谁跑快了。
- **双链路联调**：同一场景两条链路各跑一遍，比对行为必须一致。防止"仿真里好好的、真机不行"。这是当前阶段的关键验收动作。
- **B-sim / B-real**：链路 B 的两个细分——对面接仿真（现在）还是接真实驱动器（未来）。
- **回环（L3）**：链路 A 的终极测试——真编译、真加载、真读写数据转一圈，证明"这条路能走通"。

## 4. 四份契约（①②③④编号的"合同"）

三方之间的接口都定成了白纸黑字的"合同"，谁都不能随意改：

| 编号 | 是什么 | 谁拥有 |
|---|---|---|
| 契约① | 需求规格的格式（requirement_spec Schema）——AI 理解完需求后交出的结构化文档长什么样 | gc |
| 契约② | PLC 代码生成规矩（ST 子集、变量只能放 %Q 区、禁用 REAL 浮点、每个程序要有 prog_id 身份号……）——违反就**直接拒收**，不进编译 | lx |
| 契约③ | io_map——一份三方对照表：每个 IO 变量在 PLC 里叫什么/放哪、Modbus 地址是多少、仿真里绑哪个部件。三方对账全靠它 | csk |
| 契约④ | 验收准则的结构（四类准则：到值/区间/时序/不变量） | csk 起草 |

相关词：
- **draft / 冻结**：draft.2 = 第 2 版草案（还在评审）；冻结 = 定稿，之后不能随手改。
- **RFC**：改已冻结契约的正式流程——提案（说清为什么改、影响什么、怎么迁移）→ 三方评审 → 同批改文档记档案。类比"合同修订要走会签"。
- **io_list**：契约①里的 IO 变量清单（名字/类型/方向/量程），是契约③ io_map 的上游。
- **device_model**：⓪ 产出的设备模型数据。
- **prog_id**：每个场景程序的"身份证号"，写在固定地址 %QW20。验收前先核对身份，防止"测了半天测的是旧程序"。

## 5. 闸门（gate）

gc 编排器（AI 的"总调度"）流水线上的**质检工位**——生成的产物必须过闸才能往下走，不合格就打回去重生成：

- **闸门 1~4**：生成 → 静态检查（xml2st，秒级）→ 三方一致性检查 → 部署+在线验收。
- **R1~R6**：一致性检查器里的第几项检查（R5=对照 io_map 查变量，R6=拿设备描述文件跟生成的程序对账地址，防 AI 自己编造地址）。
- **一致性检查**：需求规格、PLC 程序、io_map 三方互相校对，变量名/地址必须对得上。

## 6. 测试分层（L1 / L2 / L3）

按"贵不贵、离真东西近不近"排的三层质检，**原则：便宜层能拦的问题绝不放行到贵层**：

| 层 | 干什么 | 类比 | 需要什么环境 |
|---|---|---|---|
| L1 | 静态检查：不跑代码，只"读一遍"查格式/契约 | 老师扫一眼作文有没有跑题 | 什么都不装，秒级 |
| L2 | 单元测试：跑代码逻辑本身 | 检查零件尺寸 | 普通电脑 |
| L3 | 在线验收：真编译、真运行、真读写 | 整车上路试驾 | 要编译器和运行时（PLC 工具链） |
| （集成回归） | 全部场景重跑一遍 | 出厂前全检 | run_regression.py 一键跑全部层 |

- **在线 / 离线 / SKIP**：运行时开着=在线；没开=离线，L3 自动跳过（记 SKIP，不算失败）；`--require-online` = 强制要求在线，离线就当失败（合入门禁用）。
- **pytest**：Python 的标准测试工具，报告里"pytest 100/100"就是单测 100 项全过。
- **验收脚本（scenario_*.py）**：一身两角的测试脚本——既扮演被控设备（电机、传感器），又当裁判（注入激励、检查 PLC 反应）。
- **场景（scenario）**：一个完整测试案例 = 一份 PLC 程序 + 一份验收脚本。当前看家场景 **motion3axis**（三轴运动控制），gc 侧新增 plotter3axis / plotter_circle（三轴绘图、画圆）。

## 7. PLC 侧技术名词（lx 的地盘）

- **PLC**：工业控制器，工厂设备的"大脑"，按固定周期（毫秒级）反复扫描执行控制逻辑。
- **PLCopen XML（IEC 61131-10）**：PLC 程序的标准交换格式——程序写成 XML 文本，不同厂商工具都能导入导出。**本项目规定它是唯一源码**。
- **ST（结构化文本）**：PLC 编程语言之一，像 Pascal 的文本代码。XML 是"给人/工具看的"，ST 是"真正拿去编译的"；从 XML 到 ST 由转换器（xml2st）机械完成，禁止手改产物。
- **matiec / iec2c**：开源的 ST 编译器（把 ST 编译成 C），OpenPLC 内部就用它。
- **OpenPLC**：开源软 PLC——用软件模拟一台真 PLC，带网页管理和 Modbus 通信，跑在 Docker 容器里。
- **%QX / %QW / %I**：PLC 的内存分区地址。%QX=输出开关量（一个 bit，又叫"线圈"）；%QW=输出模拟量（16 位寄存器）；%I=输入区。**本项目约定：所有对外变量统一放 %Q 区**（连传感器注入也写 %Q 再读回来），这样两条链路行为一致——这是实测踩坑后的决定。
- **SafeCoilIO**：lx 封的"线圈安全读写层"。因为 OpenPLC 有个怪癖：单独写一个线圈位会**破坏相邻位**，必须整组读-改-写。凡走链路 B 写线圈必须经过它，红线。
- **CSP（周期同步位置）**：当前运动控制的架构——PLC 每周期下发一个位置点（插补），驱动器闭位置环跟着走。三层：INTERP（轨迹规划）→ DRIVE402（驱动器模型）→ MC API（标准运动控制指令）。
- **CiA402**：伺服驱动器的工业标准状态机；cw/sw = 控制字/状态字（驱动器的"命令面板"和"仪表盘"）。
- **serve.py /deploy /status**：把部署做成了 HTTP 服务——AI 编排器发一个网络请求就能部署程序、查当前状态（跑的哪个场景、身体号是多少）。
- **坑库（pitfalls）**：把 matiec/OpenPLC 的怪癖逐条记录（如保留字、浮点初值必须带小数点），AI 生成时回灌避免重踩。

## 8. 仿真侧技术名词（csk 的地盘）

- **SceneSpec**：仿真场景的描述格式（有哪些部件、尺寸、行程、IO 绑定），从它**确定性**构建出仿真场景，不是手工搭。
- **MJCF**：MuJoCo 的场景文件格式（XML），从 SceneSpec 确定性构建生成。
- **MuJoCo**：物理仿真引擎（开源、轻量、headless 友好）——项目当前唯一仿真后端（原 Isaac Sim 后端已按负责人指令废弃，2026-09-09）。
- **桥（gantry_bridge）/ 示教器**：桥 = Modbus 通信中转站，让 PLC 和仿真互相读写；示教器 = 手动操纵虚拟设备的手柄界面（像真机床的手持单元）。
- **判定引擎**：仿真跑完后自动判"合格/不合格"的裁判，输出 verdict 结论。**目前还没开工，是全闭环的关键缺口**。
- **float32/INT16 换算议题**：一个在议的接口问题——csk 的桥用 32 位浮点传数，但契约②规定 PLC 侧只有 16 位整数，**谁来做换算**？lx 建议：桥来换（PLC 侧保持简单），待三方定稿。

## 9. 看板与报告里的常用词

- **看板**（docs/协作看板.md）：三人进度墙，每人一个区块（进度表/问题/待配合），底部共同议题区 = 三方要一起拍板的事。
- **@对方 / ✅**：待配合小节里点名请求，对方办完标 ✅ 注明日期。
- **devlog**：个人技术日志（改了什么/为什么/怎么验证/踩坑解法），只在个人分支，合入主干前删除。
- **changelog**：契约/架构变更的档案账本（"为什么变成现在这样"）。
- **分支 / master / 许可制**：三人各用自己名字的常驻分支（lx/csk/gc）干活；master 是主干，**合入必须先申请负责人批准**，防止未评审代码进主干。
- **种子模式 / LLM 真生成**：gc 测编排流程时先用预置的好程序（种子）跑通全流程；换成真大模型生成叫真生成（画圆场景已真生成并通过验收）。
- **半环 / 全环 / 闭环**：整个流程转起来叫闭环。目前只有"生成→部署→验收"这半环在转（验收由脚本扮演设备）；加上物理仿真+判定+回喂才是全环。
- **归因**：出错后分析原因（读编译错误/验收失败信息，定位到坑库里对应问题）喂回 AI。
- **状态图标**：✅ 完成｜🟡 进行中/评审中｜🟨 代码就绪（缺环境验证）｜⏸ 等别人｜⬜/🔴 未开始｜❓ 待定。

## 10. 三步读懂一次进度更新

1. **看本人区块第一行"当前状态"**——一段话总结最近干的事；
2. **看进度表里非 ✅ 的行**——那就是此人当前的活；
3. **看共同议题区 🟡/🔴 的行**——那就是全项目的卡点（谁欠谁一个决定/一个接口）。
