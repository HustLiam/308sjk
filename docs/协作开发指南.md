## 2. 环境搭建（首次，约 15 分钟）

```bash
git clone https://github.com/HustLiam/308sj.git && cd 308sj
git checkout lx          # 或你的工作分支
pip install -r requirements.txt

# 验证 ①：转换器单测（无需任何运行时，必须全绿）
python -m pytest tests/ -v

# 验证 ②：看一份 PLCopen XML 转出的 ST
python src/pipeline/xml2st.py src/plc/motion3axis.xml --check

# 验证 ③（可选，lx 侧联调才需要）：起 OpenPLC 运行时
docker run -d --name openplc -p 8080:8080 -p 502:502 fdamador/openplc
python src/pipeline/run_deploy.py && python src/pipeline/scenario_motion3axis.py
```

三个验证分别对应三层能力：纯转换、纯校验、全链路。csk 侧另需 Isaac Sim 4.5 与 matiec 工具链（见其文档 §5.1 / §8）。

## 3. 分支模型、本地开发日志与 master 合入（许可制）

### 3.1 分支模型：各成员一个常驻分支

三人各用自己的常驻个人分支开发——**lx 用 `lx`、csk 用 `csk`、gc 用 `gc`**。日常开发、提交、推送都发生在自己的分支上，分支即个人工作区，不需要再拉功能分支。

### 3.2 本地开发日志（每分支一份，永不进 master）

- **路径**：`docs/devlog-<成员>.md`（如 `docs/devlog-lx.md`），提交在个人分支上（获得版本历史，换机不丢）；
- **内容边界：只做代码上的技术说明**——改了什么、为什么这么改、如何验证、踩到的技术坑与解法（编译器怪癖、参数整定过程、竞态等）。进度状态、协调配合类内容**不写这里**，写 `docs/协作看板.md`；
- 日志可以写得很详细，它是个人技术记忆，master 上永远不出现。

### 3.3 合入 master：先许可，后合并，不带日志

1. 个人分支推进到需要合入 master 时，**先在协作看板或线下向项目负责人申请许可**，等待获批；
2. 获批后，合并前先在个人分支移除日志并提交（分支历史中仍可回溯）：

   ```bash
   git rm docs/devlog-lx.md
   git commit -m "合并前移除本地开发日志"
   ```

3. 再执行 master 合并与推送；合并后可在个人分支重建日志继续记录；
4. **任何情况下 master 不包含 devlog 文件**——评审/CI 发现即打回。

### 3.4 提交与评审约定

1. **提交信息**：`模块: 变更摘要`（历史风格，如 `xml2st 防信息丢失：…`、`主方案去 CODESYS 化：…`）；
2. **合入自检**（DoD 清单为操作视图，规则源为主方案 §8.4）：
   - [ ] `python -m pytest tests/ -v` 全绿；
   - [ ] 涉及场景的：对应 `scenario_*.py` 验收通过（已验收 XML 是契约回归样例，改动契约必须全过）；
   - [ ] 涉及契约/架构的：四份文档同一批合入内同步修订；
   - [ ] `docs/协作看板.md` 本人区块已更新；
3. **评审规则**（主方案 §8.1 RACI 表）：常规改动 1 名相关方评审即可；**契约文件**的合入必须三方知情，评审人须含契约拥有方；
4. **禁止未经许可直推 master**；禁止"顺手改契约"——契约变更走 §5 流程。

## 4. 日常协作节奏

- **开工前**：看 `docs/协作看板.md`——有没有人向你提了待配合？共同议题有没有变化？
- **会话中**：卡住超过半天且依赖他人的，立刻在看板"待配合"区 @ 对方并写清依赖内容，不要闷头等；
- **收工前（六步清单，缺一不可）**：
  1. pytest 全绿；
  2. 涉及场景的验收脚本全过；
  3. **lx 文档 §5.3 场景表更新**（新场景/结果变更）；
  4. **协作看板本人区块刷新**（进度/问题/待配合）；
  5. **changelog 登记**（契约/架构/场景库变更）；
  6. **devlog 写入**（技术排障过程，合入前移除）。
- **跨方接口对接**：先在共同议题区对齐字段结构（冻结成契约），再各自写代码——避免"两边各写完再对"的返工模式。

## 5. 契约变更流程（RFC）

四份冻结契约（requirement_spec Schema / PLCopen XML 生成契约 / io_map 结构 / acceptance 四类结构，见主方案 §8.3）的任何修改：

```
起草 RFC（动机 / 影响面 / 迁移方案）
  → 看板共同议题区登记，@三方
  → 三方评审通过（48h 内未回复视为需要线下拉齐）
  → 同一 PR 内：改契约 + 改四文档 + 记 docs/changelog.md + 契约版本号升级（规则见主方案 §8.3）
```

## 6. 代码约定（按侧速查）

**通用**：Python ≥3.10；改动带测试；不引入未登记依赖（进 `requirements.txt` 前先在看板提一句）。

**lx 侧（PLC / 运动控制）**：

*新增运动控制场景的标准流程*：
1. 用 `tools/gen_scenarios.py` 或手写 XML 生成 `src/plc/<场景>.xml`（轴对象模板见《运动控制代码生成方案》§2）；
2. 声明 `prog_id AT %QW20`（当前已用 1~5，从 6 顺延）；
3. `xml2st --check` 静态校验通过；
4. `run_deploy --xml` 部署 + matiec 编译通过；
5. 编写 `scenario_<场景>.py` 验收脚本（身份校验 + 行为断言 + 全程不变量）；
6. 在线验收全绿后更新 lx 文档 §5.3 场景表 + 看板。

*matiec 避坑清单（第 1~8 条，新增场景必读）*：
- 保留字：`DT` `STEP` `Execute` `Target` `Hold`——改用 `SCAN_T` `pstep` `fire` `pos_target` `hold_req`
- FB 内禁用 `VAR CONSTANT` 块（用带初值的普通 VAR）
- INT 不能 AND/OR 位运算（cw/sw 一律 WORD）
- FB 输出不可作 VAR_IN_OUT 实参（经扫描头采样到定位字再绑定）
- BOOL→INT 需 `BOOL_TO_INT()` 显式转换
- REAL 初值必须带小数点（`50.0` 非 `50`）
- 多个同模式 FB 会被优化器合并（首个 C 代码被清空）——**解法：共用一个 FB 或将差异逻辑内联到 PLC_PRG**
- 不同 FB 的边沿检测变量必须不同名

*其他*：
- XML 是唯一源码，**永远不要手改 `workspace/program.st`**
- Modbus 线圈写入必须经 `SafeCoilIO`，禁止裸 `write_coil`
- 新增场景后必须同步更新 lx 文档 §5.3 场景表和看板（文档滞后即打回）

**csk 侧（仿真）**：SceneSpec 是封闭类型枚举，新组件先入组件库再对外；判定引擎保持确定性（不引入 LLM 判定）。

**gc 侧（智能体）**：生成器产出的 XML 必须先过 `xml2st --check` 本地闸门再进流水线；判定结论只消费 csk 的 verdict，不自行复判。

## 附：一次典型协作的完整走查（示例：新增"双轴定位+联锁"运动控制场景）

1. gc 出该场景的 requirement_spec（含 io_list 与验收准则）；
2. lx 用生成方案模板创建 `xy_pick.xml`（prog_id=3）+ `scenario_xy_pick.py`，链路 B 验收通过；
3. **lx 同步**：lx 文档 §5.3 场景表加行 + 看板更新 + changelog 登记 + devlog 记录排障过程；
4. csk 依同一 io_list 做 SceneSpec→USD，链路 A lockstep 跑通；
5. 双链路 trace 比对（lx 与 csk 在看板共同议题登记结果）；
6. gc 的编排器把该场景纳入闭环回归，全绿后冻结。

每一步的产出都落在 git 里，任何结论可回溯——这是本项目对"可复现"的基本要求。
