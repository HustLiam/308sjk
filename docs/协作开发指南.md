## 3. 开发生命周期（核心流程）

### 3.1 完整流程图

```
需求（gc 出 requirement_spec）
  │
  ▼
① 生成场景 XML（手写 或 tools/gen_scenarios.py）
  │     └─ 声明 prog_id（%QW20，当前 motion3axis=1，新场景从 2 顺延）
  │     └─ 确定轴类型（linear / rotary_modulo / rotary_finite）
  │
  ▼
② 静态校验（xml2st --check，秒级，无需运行时）
  │     └─ 不过 → 修 XML → 重试（最便宜的迭代点）
  │
  ▼
③ 部署编译（run_deploy --xml，需运行时，~15s）
  │     └─ matiec 编译失败 → 读 deploy_result.json errors → 对照避坑清单修 → 重试
  │
  ▼
④ 编写验收脚本（scenario_<场景>.py）
  │     └─ 结构：身份校验(require_program) + 行为断言(check) + 全程不变量
  │     └─ 电机仿真：位置跟踪（CSP 语义），非速度积分
  │
  ▼
⑤ 在线验收（python scenario_<场景>.py，需运行时）
  │     └─ 失败 → 诊断（见 §3.3 排障方法论）→ 修 XML 或脚本 → 重部署重跑
  │
  ▼
⑥ 文档同步（六步，缺一不可，见 §4）
  │
  ▼
⑦ 申请合入 master → 移除 devlog → 合并推送
```

### 3.2 分层测试策略

| 层 | 工具 | 耗时 | 运行时 | 跑什么 |
|---|---|---|---|---|
| 单元测试 | pytest | <3s | ❌ | 转换器逻辑、一致性检查、编排器 |
| 静态校验 | xml2st --check | <1s | ❌ | 契约合规（位宽/结构/prog_id） |
| 编译验证 | run_deploy | ~15s | ✅ | matiec 编译通过 |
| 行为验收 | scenario_*.py | 5~60s | ✅ | 定位精度、联锁、安全不变量 |
| 集成回归 | 全部场景 | ~5min | ✅ | 全部已验收场景重跑 |

**原则：能在便宜层拦截的问题绝不到贵层**——静态校验能拦的结构错误不要等 matiec 报，matiec 能拦的编译错误不要等运行时。

### 3.3 排障方法论（matiec/OpenPLC）

遇到编译或运行时错误时，按以下顺序排查：

**第一步：看 deploy_result.json 的 errors**
```bash
python -c "import json; print(json.load(open('workspace/deploy_result.json'))['errors'])"
```

**第二步：对照避坑清单（§6 lx 侧）定位已知问题**

**第三步：检查容器内实际 ST（OpenPLC 可能预处理）**
```bash
docker exec openplc bash -c "head -50 $(ls -t /workdir/webserver/st_files/*.st | head -1)"
```

**第四步：加临时诊断口（%QW 寄存器直出内部变量），部署后用 Modbus 读**
```st
(* 在 PLC_PRG 加诊断输出口 *)
dbg_var := <要看的变量>;
```

**第五步：确认不是多 FB 优化器 bug（第 8 条坑）**
- 症状：ST 看起来正确，matiec 编译通过，但运行时 FB 无输出
- 验证：交换 FB 顺序看是否"跟着走"
- 解法：共用一个 FB 或将差异逻辑内联到 PLC_PRG

### 3.4 电机仿真规范（CSP 语义）

验收脚本中的电机仿真必须遵循**位置跟踪**语义（非速度积分）：

```python
# ✅ 正确：读位置指令，以有限速度朝指令位置移动
cmd = read_reg(m, cmd_reg)    # 这是位置（CSP 设定点），不是速度！
diff = cmd - pos
step = MOTOR_RATE * DT
pos = cmd if abs(diff) <= step else pos + (step if diff > 0 else -step)
write_reg(m, fb_reg, round(pos))  # 写回编码器反馈

# ❌ 错误：把位置指令当速度积分
pos += cmd * DT  # 这会导致位置跑飞
```

## 5. 分支模型与 master 合入

### 5.1 常驻个人分支

三人各用自己的常驻个人分支——**lx 用 `lx`、csk 用 `csk`、gc 用 `gc`**。不需要功能分支。

### 5.2 本地开发日志

- 路径：`docs/devlog-<成员>.md`，提交在个人分支上
- 内容：**只做代码技术说明**（改了什么/为什么/怎么验证/踩坑解法）
- 进度协调写看板，不写 devlog；master 上永远不出现 devlog

### 5.3 合入 master（许可制）

```bash
# 1. 向负责人申请许可（看板或线下）
# 2. 获批后：
git rm docs/devlog-lx.md
git commit -m "合并前移除本地开发日志"
git push origin lx
git checkout master
git pull origin master          # ← 重要：先拉远端（可能有人推了新提交）
git merge lx
git push origin master
git checkout lx
# 3. 重建 devlog 继续
```

**注意：合入前必须 `git pull origin master`**——远端可能有其他人的提交，不拉直接推会被拒绝（已踩过两次）。

### 5.4 提交与评审

- 提交信息：`模块: 变更摘要`
- 合入自检 = §4 六步清单
- 契约文件的合入必须三方知情
- 禁止未经许可直推 master

## 7. 代码约定（按侧速查）

**通用**：Python ≥3.10；改动带测试；不引入未登记依赖。

### lx 侧（PLC / 运动控制）

**新增运动控制场景——六步标准流程：**

```
① 用 gen_scenarios.py 或手写 XML 创建 src/plc/<场景>.xml
   └─ 声明 prog_id AT %QW20（当前 motion3axis=1，新场景从 2 顺延）
   └─ 确定轴类型：linear（无回绕）/ rotary_modulo（360° 环形）/ rotary_finite（有限转角）
② python src/pipeline/xml2st.py src/plc/<场景>.xml --check
③ python src/pipeline/run_deploy.py --xml src/plc/<场景>.xml
④ 编写 src/pipeline/scenario_<场景>.py
   └─ 结构：require_program + check 断言 + invariant 全程采样
   └─ 电机仿真用位置跟踪（见 §3.4）
⑤ python src/pipeline/scenario_<场景>.py → 全绿
⑥ 文档同步（§4 六步清单）
```

**matiec 避坑清单（第 1~8 条，写场景前必读）：**

| # | 坑 | 解法 |
|---|---|---|
| 1 | 保留字：DT/STEP/Execute/Target/Hold | 改用 SCAN_T/pstep/fire/pos_target/hold_req |
| 2 | FB 内禁用 VAR CONSTANT | 用带初值的普通 VAR |
| 3 | INT 不能 AND/OR 位运算 | cw/sw 一律 WORD |
| 4 | FB 输出不可作 VAR_IN_OUT 实参 | 经扫描头采样到定位字再绑定 |
| 5 | BOOL→INT 需显式转换 | BOOL_TO_INT() |
| 6 | REAL 初值必须带小数点 | 50.0 非 50 |
| 7 | 多个同模式 FB 会被优化器合并 | **共用一个 FB 或内联到 PLC_PRG** |
| 8 | 边沿检测变量在不同 FB 必须不同名 | edge_ir / edge_rs / edge_ma |

**其他：**
- XML 是唯一源码，**永远不要手改 workspace/program.st**
- Modbus 线圈写入必须经 SafeCoilIO，禁止裸 write_coil
- 主站时序：目标寄存器先于指令上升沿建立（≥1 扫描周期）

### csk 侧（仿真）

- SceneSpec 封闭类型枚举，新组件先入组件库
- 判定引擎保持确定性（不引入 LLM 判定）

### gc 侧（智能体）

- 生成器产出必须先过 xml2st --check 本地闸门
- 判定结论只消费 csk 的 verdict
