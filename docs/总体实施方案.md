# 总体实施方案

## 面向工业自动化场景的 AI 驱动 PLC 控制代码自动生成与仿真验证闭环系统

---

## 1. 项目概述

### 1.1 项目背景与目标

传统工业自动化项目中，PLC 控制程序的编写高度依赖工程师经验，开发周期长、验证成本高，且需求理解偏差往往要到现场调试阶段才暴露。随着大语言模型（LLM）在代码生成领域的成熟，以及数字孪生与仿真技术的发展，"需求 → 代码 → 仿真 → 验证 → 迭代"的全流程自动化已成为可能。

本项目旨在设计并实现一个 AI 系统，能够：

1. **接收并理解用户自然语言指令**，解析出控制需求、工艺约束与验收标准；
2. **自动生成 IEC 61131-10（PLCopen XML）格式的 PLC 控制代码**——这是唯一的代码交付格式，全流程强制；
3. **自动生成 USD 格式的仿真环境**，描述被控对象的几何、物理与传感特性；
4. **执行控制代码并运行仿真闭环**：同一份 PLCopen XML 经 matiec 编译为 C 共享库，加载进 Isaac Sim 主进程 lockstep 执行（主链路）；另部署到 OpenPLC 软 PLC 经 Modbus TCP 交互（验收链路）——驱动虚拟设备运动、回传仿真传感器数据；
5. **采集实验结果并进行自动化验证**，判定控制逻辑是否满足需求；
6. **形成闭环迭代机制**：验证失败时将错误信息反馈给 AI 重新生成代码，持续改进直至满足要求。

### 1.2 技术栈基线（强制约定）

| 决策点 | 选型 | 说明 |
|---|---|---|
| 控制代码交付格式 | **IEC 61131-10 PLCopen XML（强制）** | 全流程唯一代码载体；控制逻辑语言为 IEC 61131-3 ST，封装于 PLCopen XML 中 |
| 代码执行引擎 | **matiec（主链路 A）+ OpenPLC v3（验收链路 B）** | A：matiec（Beremiz 项目的 IEC 61131-3 编译器）把 PLCopen XML 编译为 C 共享库，加载进仿真主进程 ctypes lockstep 调用；B：OpenPLC v3（Docker 部署，内置 matiec）作软 PLC 验收运行时，全 HTTP API、无 GUI、无许可证限制；CODESYS 版实现保留于 git 历史，作标准符合性参考 |
| 仿真环境格式 | **USD** | Isaac Sim 原生格式；场景由中间表示 SceneSpec 经确定性代码构建为 USD |
| PLC ↔ Isaac 数据交换 | **进程内函数调用（主链路 A）+ Modbus TCP（验收链路 B）** | A：每物理步"写输入镜像 → PLC 扫描 → 读输出镜像"的 ctypes 函数调用，零网络开销、完全 lockstep；B：OpenPLC 将 %QX 映射为 Modbus 线圈、%QW 映射为保持寄存器（:502），外部按 io_map 地址表轮询读写 |
| 仿真软件 | **NVIDIA Isaac Sim 4.5（headless）** | 闭环迭代不开启渲染；GUI 仅用于人工抽查与演示 |

## 2. 端到端数据流与核心工件契约

一次闭环迭代产生的全部中间产物及生产/消费关系如下（各模块的详细输入/输出见第 3 章）：

| 工件 | 格式 | 生产者 | 消费者 | 校验方式 |
|---|---|---|---|---|
| `request.json` 用户指令 | 文本 | 用户 | ① | — |
| `requirement_spec.json` 需求规格 | JSON（Schema） | ① | ②a②b④ | JSON Schema 校验 |
| `plc_project.xml` 控制代码 | **IEC 61131-10 PLCopen XML（强制）** | ②a | ③a | PLCopen 子集静态校验（xml2st）+ matiec 编译 |
| `scene.spec.json` 场景描述 | JSON（Schema） | ②b | ③b（构建输入）、④归因 | JSON Schema + 物理参数校验 |
| `scene.usda` 仿真场景 | **USD** | ③b（由 scene.spec.json 确定性构建） | ③b 自身（加载仿真） | 加载冒烟测试 |
| `io_map.json` IO 映射契约 | JSON | ②b | ③a③b④ | 与需求规格 IO 清单、ST 变量声明三方一致性检查 |

| `verdict.json` 判定结果 | JSON | ④ | ①②a②b、用户 | — |
| `report.md` 归因报告 | Markdown | ④ | 反馈 Prompt 素材 | — |

每轮迭代产物落盘于 `runs/<task>/iter_NNN/`，全量纳入 git 管理，保证任何结论可复现。

## 3. 各模块详细设计

### 3.1 需求理解模块（①）

**功能**：将用户自然语言指令转化为机器可执行、可验证的结构化需求规格。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| 用户指令 | 用户交互层 | 自然语言（文本）；可多轮澄清，歧义时 Agent 主动提问 |
| 失败反馈包 | ④（迭代时） | `verdict.json` + `report.md` + 上轮规格；用于判断失败是否源于需求歧义，必要时修订规格并回显用户确认 |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `requirement_spec.json` | ②a②b④ | JSON，通过 Schema 校验后方可下发。包含四个部分：<br>· `task_goal`：被控对象与工艺动作序列描述<br>· `io_list`：IO 清单（变量名、方向 input/output、类型 BOOL/REAL、量程、关联设备语义）——**这是 ②a 的 ST 变量声明、②b 的 io_map、③a/③b 的 IO 地址映射三方的共同源头**<br>· `constraints`：时序约束、互锁条件、异常处理策略<br>· `acceptance`：可量化验收准则（事件延迟、区域包含、禁止状态、仿真健康四类） |
| 澄清问题 / 确认请求 | 用户交互层 | 规格回显，用户确认或修正后才进入生成阶段 |

**处理要点**：LLM Agent 注入工业自动化领域知识（PLC 编程规范、典型工艺、安全联锁规则）；`acceptance` 中每条准则必须落到 3.5 节定义的四种机器可判定类型之一，否则强制退回重新组织。

### 3.2 PLC 代码生成模块（②a）

**功能**：根据需求规格生成 **IEC 61131-10 PLCopen XML 格式**的、可被 matiec 直接编译的完整工程。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| `requirement_spec.json` | ① | `task_goal` / `io_list` / `constraints` |
| 失败反馈包 | ④（迭代时） | 归因报告 + 失败准则及证据 + 相关 trace 窗口 + 上轮 `plc_project.xml` 及 diff + 迭代记忆（历史各轮"改了什么→结果如何"） |
| 领域知识库 | 静态资产 | ST 代码模式库（顺序控制、状态机、PID、联锁）PLCopen XML 模板、历史项目片段（RAG） |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `plc_project.xml` | ③a | **IEC 61131-10 PLCopen XML，强制唯一代码交付格式**。必须包含：ST 本体的 POU 定义、定位变量 IO 声明（统一 %Q 区，锚定 Modbus 映射与 IO 镜像）、资源配置；禁止 CODESYS 专有扩展命名空间。完整结构要求见 lx 文档 §3.1 |
| 代码说明 | 归因素材 | 模块/状态机结构自述，供④归因引用 |

**PLCopen XML 强制规范**：语言只用 ST、IO 用定位变量（统一 %Q 区）、一个 `PLC_PRG` 主程序、生成后三重前置校验（静态校验 → 编译 → 三方一致性）——**允许/拒绝清单、位宽表、校验器行为的权威定义见 lx 文档 §3**；编译不通过直接反馈重生成，**不进入仿真环节**，节省迭代成本。

### 3.3 仿真环境生成模块（②b）

**功能**：根据需求规格生成**场景描述（SceneSpec JSON）**与 IO 映射契约——LLM 不直接产出 USD，USD 的确定性构建由 ③b 仿真引擎承担（见 §3.4.3）。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| `requirement_spec.json` | ① | `task_goal` / `io_list`（决定需要哪些设备与 IO 绑定） |
| 场景归因反馈 | ④（迭代时） | 仅场景类失败（布局穿模、物料位置不合理、传感器遮挡等）路由到本模块 |
| 组件资产库 | 静态资产 | 预制作的 USD 组件（传送带、气缸、光电传感器、料槽、夹爪、机械臂、物料箱…），每个组件带参数规则与可绑定 quantity 清单 |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `scene.spec.json`（场景描述） | ③b（构建输入）/ ④归因 | **JSON（Schema 强制）**。设备清单、位姿、参数、投料脚本、终止条件；先过 Schema 与物理校验再交给 ③b |
| `io_map.json` | ③a③b④ | **三方映射契约**，每条记录：`plc_var`（≡ 定位变量）↔ `io_channel`（进程内 IO 镜像通道 / Modbus 地址，如 `%QX0.0` → 线圈 0、`%QW0` → 保持寄存器 0）↔ `bind`（USD prim 路径 + quantity，如 `/World/cyl_1` + `extend_cmd`），并含方向、类型、量程换算（字段结构权威见本方案 §3.3） |

**处理要点**：LLM 不直接写 USD（schema 复杂、错误难定位），只生成小语法面的 `scene.spec.json`；`type` 为封闭枚举，发明新类型会在校验被拒并精准反馈；`scene.spec` 中的投料脚本与终止条件保证同一场景可确定复现，是迭代可比较的前提。**边界**：②b 到场景描述 JSON 为止；`json→USD` 的确定性构建（组件 reference 引用 + 摆位 + 参数写入）与加载冒烟属 ③b（§3.4.3），构建器实现见 csk 文档 §4.4。

### 3.4 执行与仿真引擎（③a PLC 执行引擎 × ③b Isaac Sim 仿真引擎）

**功能**：让生成的 PLCopen XML 代码编译执行，并与 Isaac Sim 物理仿真 lockstep 联动，驱动虚拟设备运动、回传传感数据、采集全程 trace。**主链路 A**（开发/CI 闭环主力）：matiec 编译为 C 共享库，加载进仿真主进程逐物理步调用；**验收链路 B**：OpenPLC 软 PLC + Modbus TCP，证明代码可在工业级软 PLC 上运行。两链路跑**同一份 PLCopen XML 与 io_map**，差异只在运行时。

**输入**：

| 输入 | 来源 | 说明 |
|---|---|---|
| `plc_project.xml` | ② | 主链路 A：matiec 编译为 C 共享库；验收链路 B：OpenPLC HTTP 上传编译 |
| `scene.usda` + `io_map.json` | ③ | 加载进 Isaac Sim；io_map 同时驱动 IO 镜像通道与 USD 绑定 |
| 运行参数 | 编排器 | 仿真时长上限、随机种子、DLL 路径（主链路 A）/ Modbus 端点（`tcp://127.0.0.1:502`，链路 B）、扫描周期（默认与物理步同步 8.3ms）、物理步长（1/120s） |

**输出**：

| 输出 | 去向 | 内容 |
|---|---|---|
| `trace.parquet` | ④ | 每 tick 全量数据：时间戳、全部 PLC 输入/输出值（链路 B 含 Modbus 读写时间戳）、关节状态、关键物体位姿 |
| `events.json` | ④ | 离散事件（信号边沿、碰撞、物料入槽、超时） |
| `exit.json` | ④ | 结束原因（正常/超时/物料掉落/仿真发散）与链路 B Modbus 轮询延迟统计（主链路 A 进程内调用，无通信延迟） |
| `sim_log.txt` / OpenPLC 编译运行日志 | ④归因素材 | 加载错误、物理警告、PLC 异常停机 |

#### 3.4.1 PLC 侧（③a，双链路）

**主链路 A——matiec 编译 → C 共享库 → 进程内 lockstep（开发与 CI 闭环主力）**：

1. **构建流水线**：`plc_project.xml` → **xml2st（复用 PLC 侧，转换点唯一）** → `plc.st` → matiec（`iec2c`，输入为 ST 文本）→ 生成 C 代码 → gcc/MinGW 编译为共享库 `plc_logic.dll`；外层以 C shim 封装稳定接口隔离 matiec 各版本符号差异（shim/ctypes 绑定与地址表自动生成，见 csk 文档 §6.2）；
2. **执行方式**：共享库加载进 Isaac Sim 主进程，ctypes 逐物理步调用，IO 交换为函数调用级（微秒级）、零网络开销；
3. **同步语义**：1 物理步 = 1 PLC 扫描（lockstep），扫描周期即 `physics_dt`；模拟慢扫描 PLC（如 10ms/20ms）时按 `tick % N == 0` 降频调用 `plc_run`，输入输出零阶保持；PLC 与物理之间不存在竞态与时钟漂移，trace 可逐 tick 精确对账，失败归因可排除通信因素。

**验收链路 B——OpenPLC 软 PLC + Modbus TCP（工业代表性验证，已落地）**：

1. **部署流水线**（全脚本化、无 GUI、无许可证限制）：`plc_project.xml` 先过 xml2st 静态校验 → OpenPLC v3（Docker）HTTP API 上传 → 内置 matiec 编译 → 启动运行时；仓库已实现部署编排器与 POST /deploy 服务化端点；
2. **IO 映射**：运行时将 `%QX` 映射为 Modbus 线圈、`%QW` 映射为保持寄存器（Modbus TCP :502），外部按 `io_map.json` 地址表读写；位宽契约与线圈写入红线等实测结论的权威定义见 lx 文档 §3.1 / §5.2；
3. **验收语义**：与链路 A 跑同一份 XML→.st 转换产物与 io_map，差异只在运行时；用于证明代码在真实软 PLC 上可编译、可运行、行为一致（motion3axis 三轴运动控制场景已按此链路验收通过）。

#### 3.4.2 IO 数据交换（③a ⇄ ③b）（PLC → Isaac 驱动运动 / Isaac → PLC 回传传感）

**拓扑**：**主链路 A（进程内函数调用）**——`Isaac Sim 主进程 ⇄ plc_logic.dll（ctypes）`，每物理步"写输入镜像 → 跑一个 PLC 扫描 → 读输出镜像"，零网络开销；**验收链路 B（Modbus TCP）**——`OpenPLC 运行时（:502，Modbus 服务端）⇄ pymodbus 客户端（Isaac/验证侧）`，周期轮询。双向内容：

| 方向 | 机制（A / B） | 内容 | 频率 |
|---|---|---|---|
| **PLC → Isaac（驱动运动）** | A：每步 `plc_read_image` 读输出镜像；B：Modbus 读线圈/保持寄存器 | 输出值（如 `Cyl1_extend`、`Belt1_run`）→ IOBridge 换算为 USD 关节驱动目标/带速/吸附指令 | 每物理步 |
| **Isaac → PLC（传感回传）** | A：每步 `plc_write_image` 写输入镜像；B：Modbus 写线圈/寄存器 | RayCaster 光电遮挡、接触、关节位置等 → PLC 输入变量 | 每物理步 |

Isaac 侧绑定骨架（ctypes `SoftPLC` 类，进程内 lockstep 调用）的实现见 csk 文档 §6.2.3。

**时序与延迟预算**：主链路 A 的"采输入 → PLC 扫描 → 写输出 → 推物理"在同一个循环内顺序执行，IO 交换合计 <1ms，不存在网络抖动与时钟漂移——这是 A 作为闭环主力的根本原因（lockstep 时序的逐条约定见 csk 文档 §6.3）；验收链路 B 本机 Modbus TCP 轮询延迟约 1–10ms，仅最终验收轮使用。两链路对工厂级逻辑（动作、联锁、分拣，秒级）完全够用，**验收准则中的时间阈值设定不得低于 100ms**（写入需求规格约束）。

**地址契约**：IO 一律声明为定位变量，地址在代码生成期即确定（`%QX0.0` / `%QW0`…，统一 %Q 区，方向由 io_map 声明），**写入 `io_map.json`** 后全程不变；链路 A 由构建脚本按地址表自动生成 C shim 的符号引用；链路 B 按地址换算 Modbus 线圈/寄存器号，运行期直接查表。

#### 3.4.3 Isaac Sim 侧（③b）

1. **场景构建与启动**：`json→USD` 确定性构建（SceneSpec→USD 构建器，输入 ②b 的 scene.spec.json，产出 scene.usda；组件以 reference 引用资产库，只做引用+摆位+参数写入）→ 加载冒烟（2 秒：无加载错误、无 NaN、设备在位）→ headless 启动：`SimulationApp({"headless": True})` → `open_stage(scene.usda)` → `World(physics_dt=1/120)`；
2. 主循环（lockstep：每物理步先 IO 交换再推物理，与 3.4.2 时序一致）：

```
每个物理步（8.3ms）：
  ① 读仿真传感量 → plc_write_image 回写 PLC 输入镜像（两次扫描间零阶保持）
  ② plc_run(tick) 一个 PLC 扫描 → plc_read_image 读输出镜像 → IOBridge 换算 → 写关节驱动目标/带速
  ③ world.step(render=False)
  ④ trace 采样（PLC 双侧 IO + 物理状态 + 时间戳）
```

3. 传感器/执行器绑定由 `io_map.json` 实例化：光电=RayCaster 遮挡判断、气缸=prismatic 关节 + 速度限幅驱动（动作时间指标因此有意义）、传送带=接触表面速度、夹爪=SurfaceGripper 吸附。

### 3.5 验证与反馈模块（④）

**功能**：自动判定实验结果是否满足验收准则，并驱动闭环迭代。

**输入**：

| 输入 | 来源 | 说明 |
|---|---|---|
| `acceptance`（验收准则） | ① | 机器可判定四类：事件延迟 / 区域包含 / 禁止状态 / 仿真健康 |
| 编译报告 | ④ / 反馈自身 | matiec 编译结果（成功/错误列表；链路 A 为 iec2c 输出、链路 B 为 OpenPLC 编译日志）——编译发生在 ③a 的闸门，失败时错误文本回喂 ②a 定向重生成 |
| `trace.parquet / events.json / exit.json` | ③（③a③b 联合执行） | 时序、事件、结束原因与延迟统计 |

**输出**：

| 输出 | 去向 | 内容 |
|---|---|---|
| `verdict.json` | ①②a②b、用户 | **确定性规则引擎**对 trace 逐条评估，输出 PASS/FAIL + 逐条证据。通过/失败是客观可复现事实，**不由 LLM 判定**（引擎与 verdict 结构见 csk 文档 §7.1） |
| `report.md` 归因报告 | 反馈 Prompt 素材 | LLM 结合 verdict 证据 + trace 窗口做根因分析，区分代码问题/场景问题分别路由（归因与反馈机制的权威定义见 gc 文档 §3.2 / §4） |
| 反馈包 | ①②a②b | 由失败证据、相关 trace 窗口、上轮产物 diff、迭代记忆组成（组成与拼装见 gc 文档 §4） |
| `final/` 冻结快照 | 交付 | 全部准则通过时冻结该轮全部产物 |

**终止条件**：全部通过 → 冻结输出；达到迭代上限（默认 6）→ 取通过准则数最多的一轮为 best，输出失败分析报告供人工介入。

## 8. 工程治理与开发流程

> 三人协作 + 机器闭环的系统，按企业级流程约束开发过程。本节是四份文档（本方案 + 三份详细设计）共同的流程权威；三份细化文档见 `docs/`（以负责人为前缀）：《lx-PLC代码生成与执行引擎详细设计》（PLC 执行侧，lx）、《csk-仿真环境与IO闭环详细设计》（仿真验证侧，csk）、《gc-需求理解与闭环编排详细设计》（智能体与闭环侧，gc）。

### 8.1 三人分工与职责矩阵

分工代号：**PLC 执行侧 = lx**、**仿真验证侧 = csk**、**智能体与闭环侧 = gc**（下表及各文档中"××侧"均按此对应）。

| 模块 | 负责 | 评审 |
|---|---|---|
| ① 需求理解 + requirement_spec Schema | 智能体侧 | 三方 |
| ②a 生成契约 / xml2st 转换器 | PLC 侧 | 智能体侧（消费方） |
| ②a LLM 生成本体 / ST 模式库 | 智能体侧 | PLC 侧（契约方） |
| ②b 场景描述生成（SceneSpec LLM）/ io_map | 智能体侧 | 仿真侧 |
| ③a 链路 A 构建流水线（matiec→DLL+shim） | 仿真侧 | PLC 侧 |

### 8.2 分支、开发日志与合入许可

- **各成员使用各自的常驻分支开发**：lx 用 `lx`、csk 用 `csk`、gc 用 `gc`；日常提交与推送发生在个人分支；
- **本地开发日志**：个人分支维护 `docs/devlog-<成员>.md`，只做代码上的技术说明（进度协调走协作看板）；
- **master 为受保护主干，合入实行许可制**：需要合入时先向项目负责人申请，获批后方可合并推送；**本地开发日志永不进入 master**（合并前先从分支移除，分支历史保留可回溯）；
- 每个合入至少 1 名相关方评审（按上表"评审"列）；**契约文件**（见 8.3）的合入必须三方知情；
- **进度实时同步**：三人各自维护 `docs/协作看板.md` 中本人区块（进度/问题/待配合），每次工作会话结束、代码合入前更新；
- 提交信息沿用现有约定："模块: 变摘要"（如 "xml2st 防信息丢失：…"）。

### 8.3 契约变更控制（接口冻结）

- v1.0 冻结清单：① `requirement_spec` Schema（智能体侧拥有）；② PLCopen XML 生成契约与位宽表（PLC 侧文档 §3）；③ `io_map` 字段结构（本方案 §3.3 定义权威，csk 文档落地实现）；④ acceptance 四类准则结构（仿真侧文档 §5.1）；
- 变更流程：RFC（动机 / 影响面 / 迁移方案）→ 三方评审 → **四文档同一合入内同步修改** → 契约版本升级（兼容 +0.1，不兼容升主版本）→ 记录入 `docs/changelog.md`；
- 任何"顺手改契约"的合入一律打回——机器闭环的可持续性建立在契约稳定之上。

### 8.4 CI 质量门禁与完成定义（DoD）

- 每次合入触发：① 转换器单测（pytest）；② 契约回归（已验收 XML——当前为 motion3axis——必须通过 xml2st 校验）；③ 文档交叉引用检查（引用的文档名/章节号必须存在）；
- 阶段 DoD：单测绿 + 所属场景验收脚本通过 + 涉及契约的四文档同步 + changelog 登记；
- 集成里程碑：每阶段结束跑一次双链路端到端冒烟（链路 B 的场景验收脚本为现成门禁）。

### 8.5 配置与版本锁定

- 锁定并登记：OpenPLC Docker 镜像 tag、matiec commit 号、Isaac Sim 版本（4.5）、Python 与 `requirements.txt`（requests / pymodbus / pytest）、工具链 Docker 镜像；
- 工具链（matiec + gcc）整体锁进 Docker 镜像，禁止各机裸装漂移；
- `final/` 冻结时附 manifest（代码 / 场景 / io_map / 上述各版本号），保证一年后仍可复现。

### 8.6 许可合规盘点

- 依赖许可登记：OpenPLC v3、matiec（Beremiz 生态，GPL 系——以仓库 LICENSE 文件为准）、Isaac Sim（NVIDIA EULA）、pymodbus / requests（BSD / Apache 系）；
- 阶段五交付前确认 matiec 编译产物的分发边界（内部研究使用 vs 对外分发）并记录结论。
