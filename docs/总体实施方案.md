# 总体实施方案

## 面向工业自动化场景的 AI 驱动 PLC 控制代码自动生成与仿真验证闭环系统

---

## 1. 项目概述

### 1.1 项目背景与目标

传统工业自动化项目中，PLC 控制程序的编写高度依赖工程师经验，开发周期长、验证成本高，且需求理解偏差往往要到现场调试阶段才暴露。随着大语言模型（LLM）在代码生成领域的成熟，以及数字孪生与仿真技术的发展，"需求 → 代码 → 仿真 → 验证 → 迭代"的全流程自动化已成为可能。

本项目旨在设计并实现一个 AI 系统，能够：

1. **接收并理解用户自然语言指令**，解析出控制需求、工艺约束与验收标准；
2. **自动生成 IEC 61131-10（PLCopen XML）格式的 PLC 控制代码**——这是唯一的代码交付格式，全流程强制；
3. **自动生成 USD 格式的仿真环境**，描述被控对象的几何、物理与传感特性；
4. **执行控制代码并运行仿真闭环**：同一份 PLCopen XML 经 matiec 编译为 C 共享库，加载进 Isaac Sim 主进程 lockstep 执行（主链路）；另部署到 OpenPLC 软 PLC 经 Modbus TCP 交互（验收链路）——驱动虚拟设备运动、回传仿真传感器数据；
5. **采集实验结果并进行自动化验证**，判定控制逻辑是否满足需求；
6. **形成闭环迭代机制**：验证失败时将错误信息反馈给 AI 重新生成代码，持续改进直至满足要求。

### 1.2 技术栈基线（强制约定）

| 决策点 | 选型 | 说明 |
|---|---|---|
| 控制代码交付格式 | **IEC 61131-10 PLCopen XML（强制）** | 全流程唯一代码载体；控制逻辑语言为 IEC 61131-3 ST，封装于 PLCopen XML 中 |
| 代码执行引擎 | **matiec（主链路 A）+ OpenPLC v3（验收链路 B）** | A：matiec（Beremiz 项目的 IEC 61131-3 编译器）把 PLCopen XML 编译为 C 共享库，加载进仿真主进程 ctypes lockstep 调用；B：OpenPLC v3（Docker 部署，内置 matiec）作软 PLC 验收运行时，全 HTTP API、无 GUI、无许可证限制；CODESYS 版实现保留于 git 历史，作标准符合性参考 |
| 仿真环境格式 | **USD** | Isaac Sim 原生格式；场景由中间表示 SceneSpec 经确定性代码构建为 USD |
| PLC ↔ Isaac 数据交换 | **进程内函数调用（主链路 A）+ Modbus TCP（验收链路 B）** | A：每物理步"写输入镜像 → PLC 扫描 → 读输出镜像"的 ctypes 函数调用，零网络开销、完全 lockstep；B：OpenPLC 将 %QX 映射为 Modbus 线圈、%QW 映射为保持寄存器（:502），外部按 io_map 地址表轮询读写 |
| 仿真软件 | **NVIDIA Isaac Sim 4.5（headless）** | 闭环迭代不开启渲染；GUI 仅用于人工抽查与演示 |

## 3. 各模块详细设计

### 3.1 需求理解模块

**功能**：将用户自然语言指令转化为机器可执行、可验证的结构化需求规格。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| 用户指令 | 用户交互层 | 自然语言（文本）；可多轮澄清，歧义时 Agent 主动提问 |
| 失败反馈包 | ⑤（迭代时） | `verdict.json` + `report.md` + 上轮规格；用于判断失败是否源于需求歧义，必要时修订规格并回显用户确认 |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `requirement_spec.json` | ②③⑤ | JSON，通过 Schema 校验后方可下发。包含四个部分：<br>· `task_goal`：被控对象与工艺动作序列描述<br>· `io_list`：IO 清单（变量名、方向 input/output、类型 BOOL/REAL、量程、关联设备语义）——**这是 ② 的 ST 变量声明、③ 的 io_map、④ 的 IO 地址映射三方的共同源头**<br>· `constraints`：时序约束、互锁条件、异常处理策略<br>· `acceptance`：可量化验收准则（事件延迟、区域包含、禁止状态、仿真健康四类） |
| 澄清问题 / 确认请求 | 用户交互层 | 规格回显，用户确认或修正后才进入生成阶段 |

**处理要点**：LLM Agent 注入工业自动化领域知识（PLC 编程规范、典型工艺、安全联锁规则）；`acceptance` 中每条准则必须落到 3.5 节定义的四种机器可判定类型之一，否则强制退回重新组织。

### 3.2 PLC 控制代码生成模块

**功能**：根据需求规格生成 **IEC 61131-10 PLCopen XML 格式**的、可被 matiec 直接编译的完整工程。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| `requirement_spec.json` | ① | `task_goal` / `io_list` / `constraints` |
| 失败反馈包 | ⑤（迭代时） | 归因报告 + 失败准则及证据 + 相关 trace 窗口 + 上轮 `plc_project.xml` 及 diff + 迭代记忆（历史各轮"改了什么→结果如何"） |
| 领域知识库 | 静态资产 | ST 代码模式库（顺序控制、状态机、PID、联锁）PLCopen XML 模板、历史项目片段（RAG） |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `plc_project.xml` | ④a | **IEC 61131-10 PLCopen XML，强制唯一代码交付格式**。必须包含：<br>· `project/types/pous`：POU 定义，主体为 **ST 语言**（`body/ST/xhtml`）<br>· IO 变量声明为**定位变量**（POU 的 `VAR_INPUT/VAR_OUTPUT` 或全局 `globalVars`，带 `AT %IX/%QX/%IW/%QW` 地址）——**变量名、类型与 `io_list` 逐字一致，地址与 `io_map.json` 一一对应**（这是 Modbus 寄存器映射与进程内 IO 镜像的锚点）<br>· `configuration/resource`：资源配置与任务配置（主任务绑定主程序，扫描周期与仿真物理步同步）<br>· 禁止使用 CODESYS 专有扩展命名空间（保证交换性） |
| 编译报告 | ⑤ / 反馈自身 | matiec 编译结果（成功/错误列表） |
| 代码说明 | 归因素材 | 模块/状态机结构自述，供⑤归因引用 |

**PLCopen XML 强制规范（matiec 可编译子集）**：

1. 语言只用 ST；XML 元素严格符合 PLCopen `TC6_XML_V10.xsd`；
2. IO 变量一律声明为定位变量（`AT %IX/%QX/%IW/%QW`），地址与 `io_map.json` 一一对应，命名与 `io_list` 一致；程序内部变量在各 POU 的 `localVars` 中声明；
3. 一个 `PLC_PRG` 主程序 + 按需拆分的 FUNCTION_BLOCK；主程序绑定主任务，扫描周期与仿真物理步同步（默认 8.3ms，可按 tick 降频模拟慢扫描 PLC，两次扫描间零阶保持）；
4. 生成后**前置静态校验**：xml2st 静态校验（PLCopen 子集格式合法，不合法直接拒并结构化报错）→ matiec 编译（语义合法）→ 变量三方一致性检查（定位变量 ≡ `io_list` ≡ `io_map`）。编译不通过直接把 matiec 错误文本反馈重生成，**不进入仿真环节**，节省迭代成本。

### 3.3 仿真环境生成模块

**功能**：根据需求规格生成 USD 仿真场景与 IO 映射契约。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| `requirement_spec.json` | ① | `task_goal` / `io_list`（决定需要哪些设备与 IO 绑定） |
| 场景归因反馈 | ⑤（迭代时） | 仅场景类失败（布局穿模、物料位置不合理、传感器遮挡等）路由到本模块 |
| 组件资产库 | 静态资产 | 预制作的 USD 组件（传送带、气缸、光电传感器、料槽、夹爪、机械臂、物料箱…），每个组件带参数规则与可绑定 quantity 清单 |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `scene.usda` | ④b | **USD 格式（强制）**。由确定性构建器产出：组件以 reference 引用资产库 USD，构建器只做"引用 + 摆位 + 参数写入"，合法性由组件库保证 |
| `scene.spec.json` | 过程产物 / ⑤ | LLM 实际生成的场景中间表示（JSON：设备清单、位姿、参数、投料脚本、终止条件）；先过 Schema 与物理校验再转换 |
| `io_map.json` | ④a④b⑤ | **三方映射契约**，每条记录：`plc_var`（≡ 定位变量）↔ `io_channel`（进程内 IO 镜像通道 / Modbus 地址，如 `%QX0.0` → 线圈 0、`%QW0` → 保持寄存器 0）↔ `bind`（USD prim 路径 + quantity，如 `/World/cyl_1` + `extend_cmd`），并含方向、类型、量程换算 |
| 冒烟测试报告 | ⑤ / 反馈自身 | headless 加载 2 秒：无加载错误、无 NaN、设备在位 |

**处理要点**：LLM 不直接写 USD（schema 复杂、错误难定位），只生成小语法面的 `scene.spec.json`；`type` 为封闭枚举，发明新类型会在校验被拒并精准反馈；`scene.spec` 中的投料脚本与终止条件保证同一场景可确定复现，是迭代可比较的前提。

### 3.4 执行与仿真引擎（PLC × Isaac Sim，双链路）

**功能**：让生成的 PLCopen XML 代码编译执行，并与 Isaac Sim 物理仿真 lockstep 联动，驱动虚拟设备运动、回传传感数据、采集全程 trace。**主链路 A**（开发/CI 闭环主力）：matiec 编译为 C 共享库，加载进仿真主进程逐物理步调用；**验收链路 B**：OpenPLC 软 PLC + Modbus TCP，证明代码可在工业级软 PLC 上运行。两链路跑**同一份 PLCopen XML 与 io_map**，差异只在运行时。

**输入**：

| 输入 | 来源 | 说明 |
|---|---|---|
| `plc_project.xml` | ② | 主链路 A：matiec 编译为 C 共享库；验收链路 B：OpenPLC HTTP 上传编译 |
| `scene.usda` + `io_map.json` | ③ | 加载进 Isaac Sim；io_map 同时驱动 IO 镜像通道与 USD 绑定 |
| 运行参数 | 编排器 | 仿真时长上限、随机种子、DLL 路径（主链路 A）/ Modbus 端点（`tcp://127.0.0.1:502`，链路 B）、扫描周期（默认与物理步同步 8.3ms）、物理步长（1/120s） |

**输出**：

| 输出 | 去向 | 内容 |
|---|---|---|
| `trace.parquet` | ⑤ | 每 tick 全量数据：时间戳、全部 PLC 输入/输出值（链路 B 含 Modbus 读写时间戳）、关节状态、关键物体位姿 |
| `events.json` | ⑤ | 离散事件（信号边沿、碰撞、物料入槽、超时） |
| `exit.json` | ⑤ | 结束原因（正常/超时/物料掉落/仿真发散）与链路 B Modbus 轮询延迟统计（主链路 A 进程内调用，无通信延迟） |
| `sim_log.txt` / OpenPLC 编译运行日志 | ⑤归因素材 | 加载错误、物理警告、PLC 异常停机 |

#### 3.4.1 PLC 侧（④a，双链路）

**主链路 A——matiec 编译 → C 共享库 → 进程内 lockstep（开发与 CI 闭环主力）**：

1. **构建流水线**：`plc_project.xml` → matiec（`iec2c`）→ 生成 C 代码（`POUS.c` / `accessor.h` 等）→ gcc/MinGW 编译为共享库 `plc_logic.dll`；外层以 **C shim** 封装稳定接口（`plc_init / plc_run / plc_write_image / plc_read_image`），隔离 matiec 各版本间生成符号命名的差异；shim 与地址表由构建脚本按 `io_map.json` 自动生成，不手写；
2. **执行方式**：共享库加载进 Isaac Sim 主进程，ctypes 逐物理步调用，IO 交换为函数调用级（微秒级）、零网络开销；
3. **同步语义**：1 物理步 = 1 PLC 扫描（lockstep），扫描周期即 `physics_dt`；模拟慢扫描 PLC（如 10ms/20ms）时按 `tick % N == 0` 降频调用 `plc_run`，输入输出零阶保持；PLC 与物理之间不存在竞态与时钟漂移，trace 可逐 tick 精确对账，失败归因可排除通信因素。

**验收链路 B——OpenPLC 软 PLC + Modbus TCP（工业代表性验证，已落地）**：

1. **部署流水线**（全脚本化、无 GUI、无许可证限制）：`plc_project.xml` 先过 xml2st 静态校验 → OpenPLC v3（Docker）HTTP API 上传 → 内置 matiec 编译 → 启动运行时；仓库已实现部署编排器与 POST /deploy 服务化端点；
2. **IO 映射**：运行时将 `%QX` 映射为 Modbus 线圈、`%QW` 映射为保持寄存器（Modbus TCP :502），外部按 `io_map.json` 地址表读写；位宽契约（实测结论，agent 生成契约的一部分）：`INT` 挂 `%QW`，`%QD` 不映射故禁用，线圈写入存在窄范围破坏相邻位的怪癖需按字节对齐封装；
3. **验收语义**：与链路 A 跑同一份 PLCopen XML 与 io_map，差异只在运行时；用于证明代码在真实软 PLC 上可编译、可运行、行为一致（counter / sorting / pump / traffic 四场景已按此链路验收通过）。

#### 3.4.2 IO 数据交换（PLC → Isaac 驱动运动 / Isaac → PLC 回传传感）

**拓扑**：**主链路 A（进程内函数调用）**——`Isaac Sim 主进程 ⇄ plc_logic.dll（ctypes）`，每物理步"写输入镜像 → 跑一个 PLC 扫描 → 读输出镜像"，零网络开销；**验收链路 B（Modbus TCP）**——`OpenPLC 运行时（:502，Modbus 服务端）⇄ pymodbus 客户端（Isaac/验证侧）`，周期轮询。双向内容：

| 方向 | 机制（A / B） | 内容 | 频率 |
|---|---|---|---|
| **PLC → Isaac（驱动运动）** | A：每步 `plc_read_image` 读输出镜像；B：Modbus 读线圈/保持寄存器 | 输出值（如 `Cyl1_extend`、`Belt1_run`）→ IOBridge 换算为 USD 关节驱动目标/带速/吸附指令 | 每物理步 |
| **Isaac → PLC（传感回传）** | A：每步 `plc_write_image` 写输入镜像；B：Modbus 写线圈/寄存器 | RayCaster 光电遮挡、接触、关节位置等 → PLC 输入变量 | 每物理步 |

```python
# Isaac 侧绑定骨架（主链路 A，嵌入 run_sim.py 的 lockstep 循环）
class SoftPLC:
    def __init__(self, lib_path, io_layout):
        self.lib = ctypes.CDLL(lib_path)          # plc_logic.dll
        self.layout = io_layout                   # 由 io_map.json 生成的通道表

    def exchange(self, tick, inputs):
        self.lib.plc_write_image(*pack(inputs))            # ① 传感器 → 输入镜像
        self.lib.plc_run(tick)                              # ② 一个 PLC 扫描
        return self.layout.unpack(*self.lib.plc_read_image())  # ③ 输出镜像 → 驱动
```

**时序与延迟预算**：主链路 A 的"采输入 → PLC 扫描 → 写输出 → 推物理"在同一个循环内顺序执行，IO 交换合计 <1ms，不存在网络抖动与时钟漂移——这是 A 作为闭环主力的根本原因；验收链路 B 本机 Modbus TCP 轮询延迟约 1–10ms，仅最终验收轮使用。两链路对工厂级逻辑（动作、联锁、分拣，秒级）完全够用，**验收准则中的时间阈值设定不得低于 100ms**（写入需求规格约束）。

**地址契约**：IO 一律声明为定位变量，地址在代码生成期即确定（`%IX0.0` / `%QX0.0` / `%IW0` / `%QW0`…），**写入 `io_map.json`** 后全程不变；链路 A 由构建脚本按地址表自动生成 C shim 的符号引用；链路 B 按地址换算 Modbus 线圈/寄存器号（Bool 按 16 个/寄存器位打包，REAL 占 2 寄存器、字序统一大端），运行期直接查表。

#### 3.4.3 Isaac Sim 侧（④b）

1. headless 启动：`SimulationApp({"headless": True})` → `open_stage(scene.usda)` → `World(physics_dt=1/120)`；
2. 主循环（lockstep：每物理步先 IO 交换再推物理，与 3.4.2 时序一致）：

```
每个物理步（8.3ms）：
  ① 读仿真传感量 → plc_write_image 回写 PLC 输入镜像（两次扫描间零阶保持）
  ② plc_run(tick) 一个 PLC 扫描 → plc_read_image 读输出镜像 → IOBridge 换算 → 写关节驱动目标/带速
  ③ world.step(render=False)
  ④ trace 采样（PLC 双侧 IO + 物理状态 + 时间戳）
```

3. 传感器/执行器绑定由 `io_map.json` 实例化：光电=RayCaster 遮挡判断、气缸=prismatic 关节 + 速度限幅驱动（动作时间指标因此有意义）、传送带=接触表面速度、夹爪=SurfaceGripper 吸附。

### 3.5 验证与反馈模块

**功能**：自动判定实验结果是否满足验收准则，并驱动闭环迭代。

**输入**：

| 输入 | 来源 | 说明 |
|---|---|---|
| `acceptance`（验收准则） | ① | 机器可判定四类：事件延迟 / 区域包含 / 禁止状态 / 仿真健康 |
| `trace.parquet / events.json / exit.json` | ④ | 时序、事件、结束原因与延迟统计 |

**输出**：

| 输出 | 去向 | 内容 |
|---|---|---|
| `verdict.json` | ①②③、用户 | **确定性规则引擎**（pandas 对 trace 逐条评估）输出 PASS/FAIL + 逐条证据（如"t=4.286s PE1 上升沿 → t=5.431s 气缸推出，延迟 1.145s > 0.5s"）。通过/失败是客观可复现事实，**不由 LLM 判定** |
| `report.md` 归因报告 | 反馈 Prompt 素材 | LLM 结合 verdict 证据 + 相关 trace 窗口 + 当前代码/场景做根因分析，区分**代码问题**（反馈②）与**场景问题**（反馈③）分别路由 |
| 反馈包 | ①②③ | 失败准则 + 证据、相关信号窗口（±1s）、上轮产物 diff、迭代记忆（禁止回退已通过的修改） |
| `final/` 冻结快照 | 交付 | 全部准则通过时冻结该轮全部产物 |

**终止条件**：全部通过 → 冻结输出；达到迭代上限（默认 6）→ 取通过准则数最多的一轮为 best，输出失败分析报告供人工介入。

## 4. 关键技术与难点

| 关键点 | 难度 | 应对策略 |
|---|---|---|
| LLM 产出合法 PLCopen XML（matiec 可编译） | 高 | 限定 ST 子集 + xml2st 静态校验 + matiec 编译前置拦截 + 错误文本定向反馈（链路 B 已实测 4 场景全通过） |
| matiec 构建流水线与软 PLC 全流程脚本化 | 中（链路 B 已打通） | matiec→gcc 出 DLL，C shim 隔离版本符号差异；OpenPLC HTTP API 部署编排，无 GUI、无许可证限制 |
| 双链路行为一致性 | 中 | A/B 跑同一份 PLCopen XML 与 io_map，差异只在运行时；主链路 lockstep 无通信抖动；验收轮比对两侧 trace |
| USD 场景合法性与物理合理性 | 中 | LLM 只写 SceneSpec（封闭类型枚举）+ 确定性构建器 + 组件库预校核 + 冒烟测试 |
| 验收准则可计算化 | 中 | 需求阶段强制四类机器可判定结构，Schema 校验不过则退回澄清 |
| 三方变量一致性（ST 定位变量 ≡ io_list ≡ io_map） | 中 | 单一源头（io_list）生成 + 自动一致性检查，任何一方修改须同步再生成 |
| 迭代收敛性 | 高 | 错误归因定向反馈 + 迭代历史记忆 + best-effort 兜底与人工介入出口 |

## 6. 预期成果与评估指标

**预期成果**：

1. 端到端 AI 系统：自然语言指令 → IEC 61131-10 PLCopen XML + USD 仿真环境 → matiec/OpenPLC × Isaac Sim 联合执行（进程内 lockstep 主链路 + Modbus TCP 验收链路）→ 自动验证 → 闭环迭代；
2. ST 代码模式库（PLCopen XML 模板）与 USD 工业组件资产库；
3. 完整技术文档与演示系统。

**评估指标**：

- **首次生成编译通过率（matiec）**：≥ 80%；
- **闭环收敛率**：≤ 6 次迭代内通过全部验收准则的比例 ≥ 70%；
- **需求还原度**：验收准则覆盖率 100%（每条准则均有对应自动化检查）；
- **通信质量**：主链路进程内调用无通信开销；验收链路 Modbus TCP 端到端延迟 p99 ≤ 20ms，无效轮次率 ≤ 2%；
- **端到端耗时**：单需求从输入到验证通过 ≤ 30 分钟（视仿真规模）。

## 7. 风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| LLM 幻觉导致 XML 结构/逻辑错误且难归因 | 迭代不收敛 | XSD + 编译双重前置校验；错误文本结构化反馈；保留人工介入出口 |
| 双链路行为不一致导致验收争议 | 验证结论失真 | 同一份 XML+io_map 双链路运行；主链路 lockstep 排除通信因素；验收轮全量 trace 比对；时间阈值 ≥100ms |
| matiec 生成代码符号命名随版本变化 | 升级工具链后构建失败 | C shim 隔离版本差异（地址表由构建脚本自动生成，不手写）；工具链锁定于 Docker 镜像 |
| 复杂场景仿真耗时长 | 迭代效率低 | headless 无渲染运行为主；早期迭代允许降精度物理，最终轮全精度确认 |
| 验收准则定义模糊 | 验证结果不可信 | 需求阶段强制四类可判定结构，Schema 校验不通过退回澄清 |
| 时序要求严苛的伺服级场景 | 适用范围受限 | 进程内链路延迟本可达微秒级，但本期仍定位于工厂级逻辑（≥100ms 时序）；伺服级列为二期（提高物理步/扫描频率即可复用同一框架） |
