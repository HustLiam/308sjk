# 总体实施方案

## 面向工业自动化场景的 AI 驱动 PLC 控制代码自动生成与仿真验证闭环系统

---

## 1. 项目概述

### 1.1 项目背景与目标

传统工业自动化项目中，PLC 控制程序的编写高度依赖工程师经验，开发周期长、验证成本高，且需求理解偏差往往要到现场调试阶段才暴露。随着大语言模型（LLM）在代码生成领域的成熟，以及数字孪生与仿真技术的发展，"需求 → 代码 → 仿真 → 验证 → 迭代"的全流程自动化已成为可能。

本项目旨在设计并实现一个 AI 系统，能够：

1. **接收并理解用户自然语言指令**，解析出控制需求、工艺约束与验收标准；
2. **自动生成 IEC 61131-10（PLCopen XML）格式的 PLC 控制代码**——这是唯一的代码交付格式，全流程强制；
3. **自动生成 USD 格式的仿真环境**，描述被控对象的几何、物理与传感特性；
4. **在 CODESYS 软 PLC 中执行控制代码，在 Isaac Sim 中运行仿真环境**，软 PLC 通过 OPC UA 将输出数据发送到 Isaac Sim 驱动虚拟设备运动，仿真传感器数据经 OPC UA 回传给软 PLC；
5. **采集实验结果并进行自动化验证**，判定控制逻辑是否满足需求；
6. **形成闭环迭代机制**：验证失败时将错误信息反馈给 AI 重新生成代码，持续改进直至满足要求。

### 1.2 技术栈基线（强制约定）

| 决策点 | 选型 | 说明 |
|---|---|---|
| 控制代码交付格式 | **IEC 61131-10 PLCopen XML（强制）** | 全流程唯一代码载体；控制逻辑语言为 IEC 61131-3 ST，封装于 PLCopen XML 中 |
| 代码执行引擎 | **CODESYS** | CODESYS Development System（IDE）+ CODESYS Control Win V3 x64（软 PLC 运行时，Windows 服务方式运行） |
| 仿真环境格式 | **USD** | Isaac Sim 原生格式；场景由中间表示 SceneSpec 经确定性代码构建为 USD |
| PLC ↔ Isaac 数据交换 | **OPC UA** | CODESYS 运行时内置 OPC UA Server；Isaac 侧以 asyncua 客户端订阅输出、回写传感器输入。注：经典 OPC DA 依赖 Windows COM、无 Python 生态支持，不采用；本文"OPC"均指 OPC UA |
| 仿真软件 | **NVIDIA Isaac Sim 4.5（headless）** | 闭环迭代不开启渲染；GUI 仅用于人工抽查与演示 |

## 3. 各模块详细设计

### 3.1 需求理解模块

**功能**：将用户自然语言指令转化为机器可执行、可验证的结构化需求规格。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| 用户指令 | 用户交互层 | 自然语言（文本）；可多轮澄清，歧义时 Agent 主动提问 |
| 失败反馈包 | ⑤（迭代时） | `verdict.json` + `report.md` + 上轮规格；用于判断失败是否源于需求歧义，必要时修订规格并回显用户确认 |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `requirement_spec.json` | ②③⑤ | JSON，通过 Schema 校验后方可下发。包含四个部分：<br>· `task_goal`：被控对象与工艺动作序列描述<br>· `io_list`：IO 清单（变量名、方向 input/output、类型 BOOL/REAL、量程、关联设备语义）——**这是 ② 的 ST 变量声明、③ 的 io_map、④ 的 OPC UA 节点三方的共同源头**<br>· `constraints`：时序约束、互锁条件、异常处理策略<br>· `acceptance`：可量化验收准则（事件延迟、区域包含、禁止状态、仿真健康四类） |
| 澄清问题 / 确认请求 | 用户交互层 | 规格回显，用户确认或修正后才进入生成阶段 |

**处理要点**：LLM Agent 注入工业自动化领域知识（PLC 编程规范、典型工艺、安全联锁规则）；`acceptance` 中每条准则必须落到 3.5 节定义的四种机器可判定类型之一，否则强制退回重新组织。

### 3.2 PLC 控制代码生成模块

**功能**：根据需求规格生成 **IEC 61131-10 PLCopen XML 格式**的、可被 CODESYS 直接导入编译的完整工程。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| `requirement_spec.json` | ① | `task_goal` / `io_list` / `constraints` |
| 失败反馈包 | ⑤（迭代时） | 归因报告 + 失败准则及证据 + 相关 trace 窗口 + 上轮 `plc_project.xml` 及 diff + 迭代记忆（历史各轮"改了什么→结果如何"） |
| 领域知识库 | 静态资产 | ST 代码模式库（顺序控制、状态机、PID、联锁）PLCopen XML 模板、历史项目片段（RAG） |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `plc_project.xml` | ④a | **IEC 61131-10 PLCopen XML，强制唯一代码交付格式**。必须包含：<br>· `project/types/pous`：POU 定义，主体为 **ST 语言**（`body/ST/xhtml`）<br>· `types/globalVars`：全局变量表 `GVL_IO`——所有外部 IO 变量在此声明，**变量名、类型与 `io_list` 逐字一致**（这是 OPC UA 暴露与 io_map 映射的锚点）<br>· `configuration/resource`：资源配置与任务配置（10ms 循环主任务）<br>· 禁止使用 CODESYS 专有扩展命名空间（保证交换性） |
| 编译报告 | ⑤ / 反馈自身 | CODESYS 无头编译结果（成功/错误列表） |
| 代码说明 | 归因素材 | 模块/状态机结构自述，供⑤归因引用 |

**PLCopen XML 强制规范（CODESYS 可编译子集）**：

1. 语言只用 ST；XML 元素严格符合 PLCopen `TC6_XML_V10.xsd`；
2. IO 变量集中在 `GVL_IO` 全局变量表，命名与 `io_list` 一致；程序内部变量在各 POU 的 `localVars` 中声明；
3. 一个 `PLC_PRG` 主程序 + 按需拆分的 FUNCTION_BLOCK；任务配置绑定 `PLC_PRG`，周期 10ms；
4. 生成后**前置静态校验**：XSD 校验（格式合法）→ CODESYS 脚本化导入并触发编译（语义合法）→ 变量三方一致性检查（`GVL_IO` ≡ `io_list` ≡ `io_map`）。编译不通过直接把 CODESYS 错误文本反馈重生成，**不进入仿真环节**，节省迭代成本。

### 3.3 仿真环境生成模块

**功能**：根据需求规格生成 USD 仿真场景与 IO 映射契约。

**输入**：

| 输入 | 来源 | 形式与约束 |
|---|---|---|
| `requirement_spec.json` | ① | `task_goal` / `io_list`（决定需要哪些设备与 IO 绑定） |
| 场景归因反馈 | ⑤（迭代时） | 仅场景类失败（布局穿模、物料位置不合理、传感器遮挡等）路由到本模块 |
| 组件资产库 | 静态资产 | 预制作的 USD 组件（传送带、气缸、光电传感器、料槽、夹爪、机械臂、物料箱…），每个组件带参数规则与可绑定 quantity 清单 |

**输出**：

| 输出 | 去向 | 内容与格式 |
|---|---|---|
| `scene.usda` | ④b | **USD 格式（强制）**。由确定性构建器产出：组件以 reference 引用资产库 USD，构建器只做"引用 + 摆位 + 参数写入"，合法性由组件库保证 |
| `scene.spec.json` | 过程产物 / ⑤ | LLM 实际生成的场景中间表示（JSON：设备清单、位姿、参数、投料脚本、终止条件）；先过 Schema 与物理校验再转换 |
| `io_map.json` | ④a④b⑤ | **三方映射契约**，每条记录：`plc_var`（≡ GVL_IO 变量）↔ `opcua_node`（CODESYS OPC UA 节点）↔ `bind`（USD prim 路径 + quantity，如 `/World/cyl_1` + `extend_cmd`），并含方向、类型、量程换算 |
| 冒烟测试报告 | ⑤ / 反馈自身 | headless 加载 2 秒：无加载错误、无 NaN、设备在位 |

**处理要点**：LLM 不直接写 USD（schema 复杂、错误难定位），只生成小语法面的 `scene.spec.json`；`type` 为封闭枚举，发明新类型会在校验被拒并精准反馈；`scene.spec` 中的投料脚本与终止条件保证同一场景可确定复现，是迭代可比较的前提。

### 3.4 执行与仿真引擎（CODESYS × Isaac Sim）

**功能**：让生成的 PLCopen XML 代码在 CODESYS 软 PLC 中运行，通过 OPC UA 驱动 Isaac Sim 中的虚拟设备运动，并采集全程数据。

**输入**：

| 输入 | 来源 | 说明 |
|---|---|---|
| `plc_project.xml` | ② | 经脚本化流程导入 CODESYS |
| `scene.usda` + `io_map.json` | ③ | 加载进 Isaac Sim；io_map 同时驱动 OPC UA 节点绑定 |
| 运行参数 | 编排器 | 仿真时长上限、随机种子、OPC UA 端点（`opc.tcp://127.0.0.1:4840`）、PLC 任务周期（10ms）、物理步长（1/120s） |

**输出**：

| 输出 | 去向 | 内容 |
|---|---|---|
| `trace.parquet` | ⑤ | 每 tick 全量数据：时间戳、全部 PLC 输入/输出值（含 OPC UA 通知到达时间戳）、关节状态、关键物体位姿 |
| `events.json` | ⑤ | 离散事件（信号边沿、碰撞、物料入槽、超时） |
| `exit.json` | ⑤ | 结束原因（正常/超时/物料掉落/仿真发散）与 OPC UA 延迟统计（p50/p99，超阈值判无效轮次） |
| `sim_log.txt` / CODESYS 日志 | ⑤归因素材 | 加载错误、物理警告、PLC 异常停机 |

#### 3.4.1 CODESYS 侧（④a）

1. **脚本化流水线**（CODESYS Script Engine，IronPython，命令行 `CODESYS.exe --runscript ...` 无头执行）：新建工程 → **导入 `plc_project.xml`（PLCopen XML import）** → 添加符号配置并勾选 `GVL_IO` 全部变量 → 编译 → 若报错输出错误列表（反馈②）→ 通过则下载到本机 CODESYS Control Win 运行时 → 登录并启动；
2. **运行时配置**：软 PLC 以 Windows 服务常驻；启用运行时内置 **OPC UA Server**（端点 4840，本机回环），暴露 `GVL_IO` 符号；
3. **许可注意**：Control Win 演示版有连续运行时长限制（约 2 小时，以版本许可说明为准），编排器在看门狗中于迭代间自动重启运行时；
4. **同步语义**：主任务 10ms 循环；输出变量由 PLC 写入，输入变量（传感器回写）在两次扫描间保持（零阶保持）。

#### 3.4.2 OPC UA 数据交换（PLC → Isaac 驱动运动 / Isaac → PLC 回传传感）

**拓扑**：`CODESYS OPC UA Server（软 PLC 进程内） ⇄ asyncua OPC UA Client（Isaac Sim 主进程内）`，双向：

| 方向 | OPC UA 机制 | 内容 | 频率 |
|---|---|---|---|
| **PLC → Isaac（驱动运动）** | 客户端 `create_subscription` + `MonitoredItems` 订阅 `GVL_IO` 输出节点，数据变更推送 | 输出值（如 `Cyl1_extend`、`Belt1_run`）→ IOBridge 换算为 USD 关节驱动目标/带速/吸附指令 | 发布间隔 10ms |
| **Isaac → PLC（传感回传）** | 客户端每 N 个物理步**批量 write_values** 到 `GVL_IO` 输入节点 | RayCaster 光电遮挡、接触、关节位置等 → PLC 输入变量 | 每 10ms 一次（批量单次调用） |

```python
# Isaac 侧桥接骨架（嵌入 run_sim.py 的仿真循环）
class PlcOpcUaBridge:
    async def start(self, endpoint, io_map):
        self.client = Client(endpoint)                    # opc.tcp://127.0.0.1:4840
        await self.client.connect()
        self.sub = await self.client.create_subscription(10, self)   # 10ms
        out_nodes = [self.client.get_node(m["opcua_node"]) for m in io_map if m["dir"] == "output"]
        await self.sub.subscribe_data_changes(out_nodes)             # 输出 → 本地镜像（ZOH）

    def datachange_notification(self, node, val, data):
        self.image[node.nodeid.to_string()] = (val, self.loop_time())  # 记录到达时间戳（延迟监控）

    async def push_sensors(self, sensor_values):
        nodes  = [self.client.get_node(m["opcua_node"]) for m in io_map if m["dir"] == "input"]
        await self.client.write_values(nodes, list(sensor_values))     # 批量回写
```

**时序与延迟预算**：传感器回传（≤10ms）→ PLC 扫描（10ms）→ 输出订阅推送（≤10ms）→ 物理响应，端到端典型 10–40ms、最坏约 50ms。该量级对工厂级逻辑（动作、联锁、分拣，秒级）完全够用；因此**验收准则中的时间阈值设定不得低于 100ms**（写入需求规格约束）。每次通知带到达时间戳，p99 延迟超 50ms 的轮次判为无效并重跑（防止把通信抖动误判为控制逻辑错误）。

**节点寻址**：`GVL_IO` 符号在 CODESYS OPC UA Server 下按符号路径生成 NodeID（形如 `ns=3;s=|var|...GVL_IO.Cyl1_extend`，具体命名空间索引随工程装载顺序变化）；首次部署后由脚本浏览服务器确认实际 NodeID，**固化进 `io_map.json`**，运行期直接查表。

#### 3.4.3 Isaac Sim 侧（④b）

1. headless 启动：`SimulationApp({"headless": True})` → `open_stage(scene.usda)` → `World(physics_dt=1/120)`；
2. 主循环（asyncio 单事件循环同时驱动仿真步进与 OPC UA）：

```
每个物理步（8.3ms）：
  ① 读仿真传感量 → 每 N 步批量 write_values 回写 PLC 输入节点（N≈1~2，凑足 10ms）
  ② 输出镜像（订阅推送，零阶保持）→ IOBridge 换算 → 写关节驱动目标/带速
  ③ world.step(render=False)
  ④ trace 采样（PLC 双侧 IO + 物理状态 + 时间戳）
```

3. 传感器/执行器绑定由 `io_map.json` 实例化：光电=RayCaster 遮挡判断、气缸=prismatic 关节 + 速度限幅驱动（动作时间指标因此有意义）、传送带=接触表面速度、夹爪=SurfaceGripper 吸附。

### 3.5 验证与反馈模块

**功能**：自动判定实验结果是否满足验收准则，并驱动闭环迭代。

**输入**：

| 输入 | 来源 | 说明 |
|---|---|---|
| `acceptance`（验收准则） | ① | 机器可判定四类：事件延迟 / 区域包含 / 禁止状态 / 仿真健康 |
| `trace.parquet / events.json / exit.json` | ④ | 时序、事件、结束原因与延迟统计 |

**输出**：

| 输出 | 去向 | 内容 |
|---|---|---|
| `verdict.json` | ①②③、用户 | **确定性规则引擎**（pandas 对 trace 逐条评估）输出 PASS/FAIL + 逐条证据（如"t=4.286s PE1 上升沿 → t=5.431s 气缸推出，延迟 1.145s > 0.5s"）。通过/失败是客观可复现事实，**不由 LLM 判定** |
| `report.md` 归因报告 | 反馈 Prompt 素材 | LLM 结合 verdict 证据 + 相关 trace 窗口 + 当前代码/场景做根因分析，区分**代码问题**（反馈②）与**场景问题**（反馈③）分别路由 |
| 反馈包 | ①②③ | 失败准则 + 证据、相关信号窗口（±1s）、上轮产物 diff、迭代记忆（禁止回退已通过的修改） |
| `final/` 冻结快照 | 交付 | 全部准则通过时冻结该轮全部产物 |

**终止条件**：全部通过 → 冻结输出；达到迭代上限（默认 6）→ 取通过准则数最多的一轮为 best，输出失败分析报告供人工介入。

## 4. 关键技术与难点

| 关键点 | 难度 | 应对策略 |
|---|---|---|
| LLM 产出合法 PLCopen XML（CODESYS 可编译） | 高 | 限定 ST 子集 + PLCopen XSD 校验 + CODESYS 无头编译前置拦截 + 错误文本定向反馈 |
| CODESYS 全流程脚本化（导入/编译/下载/启停） | 中高 | CODESYS Script Engine 命令行驱动；看门狗管理运行时生命周期（含演示版时长限制） |
| OPC UA 通信延迟与确定性 | 中 | 10ms 订阅 + 批量回写；逐通知时间戳监控，p99>50ms 判无效轮次；验收时间阈值 ≥100ms 约束写入需求规格 |
| USD 场景合法性与物理合理性 | 中 | LLM 只写 SceneSpec（封闭类型枚举）+ 确定性构建器 + 组件库预校核 + 冒烟测试 |
| 验收准则可计算化 | 中 | 需求阶段强制四类机器可判定结构，Schema 校验不过则退回澄清 |
| 三方变量一致性（ST GVL ≡ io_list ≡ io_map） | 中 | 单一源头（io_list）生成 + 自动一致性检查，任何一方修改须同步再生成 |
| 迭代收敛性 | 高 | 错误归因定向反馈 + 迭代历史记忆 + best-effort 兜底与人工介入出口 |

## 6. 预期成果与评估指标

**预期成果**：

1. 端到端 AI 系统：自然语言指令 → IEC 61131-10 PLCopen XML + USD 仿真环境 → CODESYS × Isaac Sim 联合执行（OPC UA 数据交换）→ 自动验证 → 闭环迭代；
2. ST 代码模式库（PLCopen XML 模板）与 USD 工业组件资产库；
3. 完整技术文档与演示系统。

**评估指标**：

- **首次生成 CODESYS 编译通过率**：≥ 80%；
- **闭环收敛率**：≤ 6 次迭代内通过全部验收准则的比例 ≥ 70%；
- **需求还原度**：验收准则覆盖率 100%（每条准则均有对应自动化检查）；
- **通信质量**：OPC UA 端到端延迟 p99 ≤ 50ms，无效轮次率 ≤ 2%；
- **端到端耗时**：单需求从输入到验证通过 ≤ 30 分钟（视仿真规模）。

## 7. 风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| LLM 幻觉导致 XML 结构/逻辑错误且难归因 | 迭代不收敛 | XSD + 编译双重前置校验；错误文本结构化反馈；保留人工介入出口 |
| OPC UA 延迟抖动被误判为控制逻辑错误 | 验证结论失真 | 逐通知时间戳监控 + 无效轮次重跑机制；验收时间阈值 ≥100ms |
| CODESYS 演示许可限制 / 脚本化 API 版本差异 | 长时间 CI 受阻 | 迭代间自动重启运行时；脚本层做版本适配封装；必要时采购正式许可 |
| 复杂场景仿真耗时长 | 迭代效率低 | headless 无渲染运行为主；早期迭代允许降精度物理，最终轮全精度确认 |
| 验收准则定义模糊 | 验证结果不可信 | 需求阶段强制四类可判定结构，Schema 校验不通过退回澄清 |
| 时序要求严苛的伺服级场景超出 OPC UA 能力 | 适用范围受限 | 本期明确定位于工厂级逻辑（≥100ms 时序）；伺服级需求列为二期（届时评估 EtherCAT/共享内存通道） |
